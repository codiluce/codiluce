Correct invalidation for actual SQLite readers

A read-only history connection uses its own PRAGMA data_version to detect commits made by another connection. Unchanged public node/page requests avoid rereading and decoding the full registry. After a commit, exact saved snapshot/state text determines whether layout caches must be invalidated; unrelated metadata commits preserve existing placements. SQLite documents that versions are meaningful only within the same connection and do not change for that connection’s own commits: official data_version semantics.

Writable callers reread the saved registry so their own transaction changes and rollbacks are visible. Changing the history connection clears cached snapshot data and rename mappings. Removed/incompatible registries correctly fall back to fresh layout. Invalid JSON continues to raise an error on each read until a valid replacement arrives, rather than being silently cached as an absent registry.

Six real SQLite regressions cover external same-ID replacement, writable updates/rollback, unchanged-page and unrelated-commit behavior, registry removal/version replacement, connection changes, and repeated malformed-JSON failure/recovery. The unchanged-reader fixture performs 100 node requests with a single full registry read, then confirms one additional read for an unrelated commit.
