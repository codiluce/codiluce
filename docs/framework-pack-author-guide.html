Framework pack-author guide

Capabilities and versionsPack-author guideImplementation roadmap

A pack turns a proven source registration into graph facts with original ownership, routing semantics and visible gaps. Start with a small qualified contract and its negative cases, then expand it through versioned fixtures.

1. Define the qualified contract

Record the canonical dependency, reviewed version family, entrypoint/registration API, required target inputs, supported path/method/handler forms and unsupported competitors. Separate original-source proof from runtime activation. A valid declaration or a familiar method name is insufficient to prove a reachable endpoint.

Use the version matrix and a neighboring adapter as a starting point. Express mounts, Flask blueprint snapshots, FastAPI snapshot/live inclusion, Rails draw files, Spring ordered builders, ASP.NET endpoint policy and Rust filter composition have different dispatch contracts.

For each claim, name a conformance input, its exact expected outcome and its failure boundary. Keep dynamic setup and unknown options visible with a reason; do not convert missing proof into an exact match.

2. Choose the actual integration path

TypeScript and component packs
Implement TypeScriptFrameworkPack in src/analysis/frameworks/typescript-pack.ts. Its id, version, applies(scope) and declare(scope) hooks run within the language cache unit. declare runs after ordinary declarations and before references/effects. Use includeEmbedded for original component inputs; optional finish(scope) runs after behavior extraction. Add the pack to typescriptFrameworkPacks in frameworks/index.ts.
Other language services
Consume that language's serializable syntax and resolver/symbol service. Follow the existing Python, Go, Ruby, JVM, C# or Rust integration in languages/. An Analyzer has name, version and asynchronous analyze(context). Wire it into the real pipeline and its language transaction; include any separately run pack versions in cache inputs and run metadata.
New structural languages
Add recognition and the code-language inventory, pinned grammar/queries/licenses, original declaration extraction, partial/failed outcomes, native dispatch and shipped assets. Update STRUCTURAL_LANGUAGES, the grammar manifest and capability documentation. Recognition does not imply semantic analysis.
Registry constraints
AnalysisRegistry rejects duplicate authoritative languages, missing dependencies and cycles. The current pipeline is wired explicitly in src/pipeline/index.ts; registering a generic pack alone does not make it execute.

Declare inline handlers with declareInlineHandler before calls and HTTP extraction so every compiler instance of the original site has its correct owner. Reuse named handlers instead of inventing generated functions.

3. Keep source, imports and ownership trustworthy

Read targets through IndexedSources or the language's validated provider. Consult indexed file/directory inventories for existence, exclusion, ambiguity and absence. Compiler-owned standard libraries are a separate boundary. Do not bypass the scan with disk discovery, execute config modules, install target packages, invoke build tools or expand runtime hooks.

Keep offsets in original UTF-16 source and ranges in one-based lines/columns. Use SourceText and established embedded mapping helpers. Cover CRLF, emoji, tabs, multiple declarations on one line and malformed regions. Virtual/compiler-only inputs must not become generated graph files or synthetic source locations. Component module/instance and browser/server/static scopes remain distinct.

For Node APIs, use frameworkBinding, runtime-reference checks and the indexed resolver to prove the canonical imported namespace across aliases/barrels/CommonJS. Check dependency versions against the owner's actual project. Local packages with a framework name, type-only imports, mutated aliases and unqualified overloads must not borrow external API identity. Other languages use their native resolver's source/external outcomes and recorded compilation contexts.

Graph identities use repository/application, original file and semantic declaration/registration identity with normalized signatures or bounded occurrence discriminators. Absolute checkout paths and line numbers must not become canonical IDs. Preserve named declaration identity across source movement where its existing language contract requires it; historical lineage is separate from canonical identity.

4. Emit native routing and flow facts

Use RoutingContract and the pack's native path compiler. Record original pattern/dialect, exact or partial status, method sets/exclusions, server context, registration receiver/site, mounts, middleware and conditions. Preserve host/query/scheme constraints and native dispatch/fallback order when proven. Unknown candidate routes still compete within their known prefix or other bounds.

Emit api_endpoint with original registration evidence, and handles to the exact original runtime callback. Page/layout/component relationships use their appropriate route/component relation. A static build operation cannot acquire a runtime handler solely because it exports a familiar method name. Automatic framework responses retain their distinct status and absence of a user callback.

Reuse language-bound original calls and dependencies rather than matching handler names. Keep nominal references distinct from direct calls, and record injection/middleware/guard references only when their declarations bind. For outbound HTTP, add an observation with original caller/file, method, URL expression and evidence; a framework transport may adopt it only through proven registration context. Let the API matcher apply origin/proxy/application boundaries and competing routing conditions.

Verify the full page → component/event → request → endpoint → original handler flow in the existing catalog and request inspector. Include source ranges and evidence at every supported stage; a count-only assertion cannot prove handler identity or source accuracy.

5. Make cache and history replay equivalent

Choose the actual dependency scope: a Node project component, a language compilation/application context or an existing repository transaction. Use fileKey, indexed paths, manifests, configuration, provider/parser/query/grammar/profile versions and every connected consumer input. Register source reads needed by replay. Dynamic availability, ignored/symlinked candidates and absent competitors are semantic inputs too.

A cache hit restores exact declaration sites and any lazy semantic services required by later passes. Never serialize native parser handles, compiler objects, absolute temporary roots or transient diagnostics into semantic graph facts. A failed or partial provider must not persist a stronger healthy cache result. Revalidate source before replay where the transaction's contract requires it.

Cold, population, warm, dependency edits, independent uncached recomputation and materialized revisions must agree on complete entities, relations, diagnostics and original evidence. History has no working-tree semantic cache; include pack versions in run metadata and preserve resume/invalidation behavior.

6. Bound interpretation and release owned data

A static registration summary is a bounded interpreter over source facts, not execution of target code. Limit helper recursion, proof hops, node/site counts, path alternatives and state expansion. On exhaustion retain an explicit partial/unsupported outcome with its original anchor; preserve independent healthy files.

Use the native generation and source/provider admission services rather than parallelizing decoded originals without a reservation. Release source memos and original trees after consumption; catalog entries should retain detached signatures or compact facts. Account resident representations, snapshots and queued inputs separately from decoded overhead and RSS. Close and await parser/worker exit on success, failure, cancellation and missing-asset fallback.

The PHP consumer implementation under qualification demonstrates detached catalogs, one-file binding IR, validated Laravel hydration and ordered route-include metadata. Broader semantic/compiler/WASM budgets and production-history measurements are separate release gates; do not advertise a physical-memory cap based on an ownership counter.

7. Expose outcomes and keep package assets complete

Set the affected feature outcome in metadata.analysis with supported, partial, unsupported, disabled or failed and a useful reason. Add analyzer/code/file/line/entity diagnostics at the original source boundary. Missing structure or a recognized extension must not accidentally qualify calls or flows.

Rust symbol producer 2 stores call/reference outcome evidence as ordered proofRefs into the owning file’s metadata.rustSymbolEvidence version 1 table. Use rustOutcomeEvidence(file.metadata, outcome) from src/analysis/rust-evidence.ts (packaged as dist/src/analysis/rust-evidence.js) to read one full proof from either current metadata or older inline proof arrays. Every duplicate, order and public JSON field remains retained; resolved relations keep self-contained proof. Table/reference payload limits do not bound full graph bytes or physical RSS. An admission failure retains complete inline evidence, fails reference coverage and emits rust-evidence-retention-budget; it cannot qualify the compact storage profile. Symbol and router caches invalidate older producer proofs.

For grammar changes, pin artifact/source revision, runtime ABI, checksum, query input and license notice in grammars/manifest.json. Use the owned sync/build scripts and verify the shipped dist/grammars assets. A missing/corrupt main or auxiliary provider affects only its documented capability; independent language/framework work must remain usable.

8. Verify a release with complete evidence

  1. Positive contracts: canonical imports/aliases, cross-file exact callbacks, inline ownership, nesting/mounts, method/path variants and native version differences.
  2. Negative contracts: local lookalikes, type-only inputs, mutations, ambiguous targets, unmounted routers, excluded files, dynamic setup, incompatible versions and unsupported competitors.
  3. Original source: Unicode/CRLF, exact ranges, same-line declarations, incomplete syntax and absence of generated graph files.
  4. Replay and availability: cold/warm/revision equality, connected dependency/config edits, missing/corrupt assets, source/symlink races and healthy-neighbor preservation.
  5. Delivery: installed production-only tarball, CLI/API/source inspector, compiled history workers, cancellation/signals and parser-asset isolation.
  6. Performance: frozen implementation, identical admitted baseline/current workloads, alternating fresh processes, complete graph/snapshot equality and predeclared median time/process-tree-memory guards. Preserve failed observations; change the cause before claiming a successful replacement.
  7. Documentation: update reviewed versions, scope/gaps, evidence links, packaged notices and the capability catalog; regenerate and check these pages. Record native OS qualification separately from recorded target build contexts.
