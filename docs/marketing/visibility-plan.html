A practical plan for the project owner

Make Codiluce visible.
Spend at most $50.

Use your personal accounts to show one useful task, meet developers who already have that problem, and turn their experience into the next demonstration.

30 daysAbout 5 hours a weekPersonal X + LinkedIn$0 required to start

Prepared 20 October 2026 · Budget assumed to be US dollars, total for the month · Recommendations, not reach forecasts.

1. Start with a specific developer problem

My recommendation: spend the first two weeks on distribution and conversations, then decide whether any spending would help. A small account can still reach the right people through useful replies, relevant communities, and other people's editorial audiences. More announcements to the same followers give you little new information.

For this first month, focus on engineers using coding agents who struggle to follow what those agents read and change. Lead with a real task: understanding an unfamiliar part of a repository before reviewing a change. Keep maintainers and onboarding teams as secondary audiences.

The message: “Codiluce helps you understand your repository while coding agents keep changing it. Explore the code on a map, inspect the evidence behind its links, and see where connected agents are working.”

The first action: run npx codiluce@latest start . inside a repository, find a familiar file, and inspect one relationship. Node.js 22.12 or newer is required. The basic map does not need a model API key; optional model features can incur provider charges.

This narrows the first campaign without changing the project's broader positioning. Use “early preview” and explain coverage limits. A dependency map shows the relationships the analysis can establish; it does not guarantee that a change is safe.

A useful month: 10 people outside your household/team confirm trying the map, 3 return to use it for another task, and 2 voluntarily share an example or allow you to describe their experience. These are planning targets, not predicted results. Record paid participants separately.

2. Prepare one useful demonstration

Make a 20–35 second screen recording that answers one question: “What is connected to this part of the code?” Use a public repository with a supported stack and a relationship you have checked. Start with the result visible, then show the clicks that explain it.

  1. First 3 seconds: show the selected code and the question on screen. Skip the logo introduction.
  2. Next 15–20 seconds: find a file, inspect a relationship, and open its source evidence. Keep names legible on a phone.
  3. Final 5–10 seconds: show the install command and invite the viewer to try the same task on their repository.

Add captions so it works without sound. Record once, then reuse the footage as an X clip, a LinkedIn clip, one annotated screenshot, and part of a longer walkthrough. Give the agent characters a separate short clip: they attract attention, while the evidence demo explains the practical value.

The working directory already contains a 37-second launch film and its capture notes. Use it as an overview; cut or capture a task-focused clip for these posts. Its storefront repository, pull request and some activity are illustrative. Label those scenes as a demo, and use an actual user run for claims about real-world outcomes. Do not describe the film as independent adoption.

Use the existing user-flow ideas as a starting point, but recheck their old version labels, measurements and limitations before publishing. On this document's date, npm reports 0.4.0, matching package.json and the site's version. This is a metadata check, not a fresh validation of every demo.

Make the next click easy

  • Use codiluce.com as the main social destination, with a distinct campaign link for each channel. Link directly to the repository when the audience wants source and setup.
  • Pin the strongest demo on X and put the project in your LinkedIn Featured section. Add a plain description and website link to both personal profiles.
  • Check that someone unfamiliar with the project can find the command, requirements, supported stacks and preview limitations. The site's embedded demo is a scripted illustration; an actual recording adds different evidence.

3. Give X and LinkedIn different jobs

X: find active conversations

Post two original posts a week: one short demonstration and one technical lesson or response to feedback. Search for recent conversations about “understanding a codebase”, “reviewing AI code”, “Claude Code”, “coding agents” and “MCP”. Pick a handful of developers who discuss these problems in detail, rather than only large accounts.

On four days each week, spend 10 minutes reading and writing one or two useful replies. Answer the person's question first. Mention that you build Codiluce when it is relevant, and include a clip or link only when it adds something. A concrete observation about their problem gives them a reason to visit your profile.

Make the post understandable without opening a thread. Put the result in the opening line, attach the clip directly, and offer one next action. Test that approach on your account; this plan makes no claim about an algorithm favoring a particular link position, hashtag count or posting hour.

LinkedIn: explain the engineering consequence

Post once a week from your personal account. Describe a situation an engineer or tech lead recognizes: inheriting a repository, following an agent's work, or checking what a shared module touches. Use the same recording with more context about what it reveals and where analysis stops.

Leave two substantive comments a week on relevant posts by engineers you already follow. Reconnect individually with a few former colleagues or peers who actually face this problem. Ask for a short trial or critique, with an easy way to decline. Avoid generic connection requests and repeated sales messages.

For both channels: stay available after posting, answer technical questions, and turn repeated questions into the next clip. Publish a different insight from the same footage rather than repeating the launch announcement. Start in the language of the audience you already know; do not create another account to translate everything this month.

4. Reach people who do not follow you

Work down this list. Choose one community and one public launch opportunity; doing everything simultaneously will consume the month.

First: invite a few relevant people to try one task

Make a list of 15 people: former colleagues, developers already discussing code comprehension, and maintainers of repositories you can demonstrate accurately. Start with five warm contacts. Ask what they struggled to understand last week, then offer to try Codiluce on that task. Aim for three personal invitations a week and one 15-minute session a week.

Let the person drive. Observe setup, whether they understand the map, and whether they find something useful. Ask a week later whether they used it again. Request permission before publishing their words or screenshots. A public repository example is not a maintainer endorsement.

Second: contribute one community-specific demonstration

Investigate r/ClaudeAI for the agent workflow, or a community for the stack in your chosen example. Read its current rules and recent accepted posts first. Post only if your actual workflow fits; for a Claude showcase, explain Claude's real role rather than adding its name to a general advert.

Include the question, what the tool found, one limitation, your relationship to the project and how to reproduce it. Ask for technical feedback. Start with one community, participate in the discussion, and adapt any later post to a different audience. Reddit prohibits repetitive mass promotion and leaves additional rules to moderators. Source: Reddit's spam policy.

Third: make one considered Show HN submission

Use Show HN after a few outsiders have successfully tried the published package, and only if you have not already submitted substantially the same project. Link to something people can run, such as the GitHub repository, rather than a signup page. Explain the problem, approach and known limitations, and reserve time to answer questions yourself.

HN asks authors to write their own posts and comments, without generated or AI-edited text. Write the submission yourself; do not paste this document's drafts there. Do not solicit votes or comments, or delete and repost a quiet submission. Coverage is uncertain and a quiet launch is not a verdict on the product. Source: HN guidelines.

Fourth: borrow an editorial audience

  • Console: suggest the tool to hello@console.dev. Send a short explanation, source link, recording, requirements and one limitation. Its selection criteria favor useful developer tools that people can try independently. Reviews are editorial; advertising is separate and does not buy a review.
  • Changelog News: use its news submission form after signing in. Pitch the open-source project announcement and what makes it technically interesting. Its page welcomes authors' own work but excludes tutorials and commercial product pitches. Selection is discretionary.

Spend at most 20 minutes adapting each pitch. Include one sentence explaining the fit. For a personal creator who already covers this workflow, offer a reproducible example without requesting a favorable review. Make at most one polite follow-up after a week where appropriate, then stop.

5. Treat $50 as a ceiling

Default spend in week one: $0. You already have a website, docs, a package, a repository and video assets. Use free recording/editing tools you already have. There is no need to buy a social subscription or launch service to execute this plan.

Separate these sessions from organic adoption in your notes. Their value is finding friction and improving the next demonstration; they do not buy distribution.

I would skip paid ads this month. LinkedIn advertises a minimum daily budget starting at $10, so a $50 ceiling leaves little room to learn through several experiments. I would also postpone X boosts, directory fees and sponsorships until a message has produced confirmed use organically.

6. A four-week schedule you can maintain

Budget about five hours each week: 75 minutes for content, 60 for replies and follow-up, 45 for personal invitations or a trial, 90 for that week's distribution task, and 30 to review results. Reuse assets to keep within the limit.

Week 1 · Make it easy to understand and try

Record the task demo, check the published install path with a volunteer, update your personal profiles, and pin/feature the demo. Write the 15-person list and invite the first three people. Publish two X posts and one LinkedIn post. Record a baseline for visits, stars and confirmed trials.

Deliverable: one reusable demonstration and at least one observed first use.

Week 2 · Test the message with a relevant community

Continue the social rhythm and personal invitations. Publish one allowed community post based on the demo. Run one feedback session. If volunteers are scarce, use the first $10 session offer. Fix or explain the biggest onboarding obstacle before seeking broader exposure.

Deliverable: a clearer pitch, concrete objections, and a decision about launch readiness.

Week 3 · Reach an existing audience

If ready, make the Show HN submission and stay available for discussion. Submit to Console and Changelog on separate days. Let these activities replace routine outreach and one social post if needed to stay within five hours. If setup still blocks people, delay the launch and spend this week resolving that friction.

Deliverable: one substantive public launch and two editorial pitches, or a better first-run experience.

Week 4 · Publish evidence and choose what to repeat

Follow up with the first users. With permission, publish one specific account of what someone learned and where the tool fell short. Alternatively, write a walkthrough of your own verified public-repository example on DEV or your existing blog. Reuse it for the week's posts. Compare confirmed use by source and choose the best channel for next month.

Deliverable: one lasting example and a decision based on use rather than impressions.

If you have only two hours a week: publish one demo adapted for both accounts, make two personal invitations, and answer replies. Run the broader launch sequence over two months.

8. Measure use, then choose the next move

Keep a simple private note or spreadsheet. For each post or invitation record: date, audience, problem shown, source link, website visits if available, replies from relevant developers, confirmed first uses, repeat uses, time spent and dollars spent. Use initials or a handle only when needed; do not put private conversations in this public document.

The website source already includes Google Analytics in production. If you have access to its property, use campaign links such as the following and check campaign reporting after opening one test link. Access and current reporting have not been verified for this plan.

https://codiluce.com/?utm_source=x&utm_medium=social&utm_campaign=visibility_30d&utm_content=evidence_demo
https://codiluce.com/?utm_source=linkedin&utm_medium=social&utm_campaign=visibility_30d&utm_content=evidence_demo

For community and editorial referrals, record the source even if it strips campaign tags. Ask trial participants how they found the project. A website visit, copied command, npm download or GitHub star does not prove someone successfully used the local app. Confirm first use through an optional reply, issue, screenshot or observed session; confirm repeat use with a later check-in. No new product telemetry is needed to start.

  • Few relevant visits after two weeks: change where you distribute. Try a more specific conversation or community before making more content.
  • Visits and questions, but few trials: tighten the demonstration and invitation. Ask two visitors what stopped them; do not infer the reason from analytics alone.
  • People try it but get stuck: fix setup or narrow the supported example before the larger launch.
  • People try it once but do not return: find out whether the task was useful and recurring. More impressions may not solve this.
  • One channel produces repeat users: give it most of next month's effort and publish another example for that audience.

Review once a week. With small samples, these are clues, not statistically reliable comparisons. Paid feedback can explain a problem but should not be counted as evidence that an acquisition channel works.

9. What can wait

Broad launch directories, Product Hunt, additional social accounts and daily posting can wait until the first-run path and message have worked for a few people. A launch badge is less useful than a reproducible example someone can share with a colleague.

GitHub discovery is already partly covered: the repository currently has relevant topics including code-comprehension, code-map, mcp and static-analysis. Keep those and the description accurate; adding tags is not this month's main task. GitHub explains how topics support discovery.

An MCP Registry listing is a later discovery task. Check whether Codiluce is listed before doing any work. The official flow requires namespace authentication and verification of the referenced published package; for npm it uses an mcpName field. Plan it with a future release if metadata changes are needed. A listing is not a feature placement, and this document does not establish that it will generate traffic. Official publishing guide.
