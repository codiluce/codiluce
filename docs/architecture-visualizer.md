# Codiluce — Code & Architecture Visualizer

Codiluce is the project name, its tagline is "Bring your code to light", and the npm command is `codiluce`.

## 1. Supported repository structure

Codiluce supports repositories containing Next.js and Laravel applications. A typical repository uses the following structure:

- `frontend/`: Next.js, React, TypeScript, Sass; App Router under `src/app`, components under `src/components`, HTTP wrappers under `src/services`, hooks under `src/hooks`. A common `tsconfig.json` alias maps `@/*` to `./src/*`.
- `backend/`: Laravel / PHP, Composer PSR-4 `App\\` → `app/`. Routes under `routes/`; controllers in `app/Http/Controllers`, Eloquent models in `app/Models`, services in `app/Services`, migrations in `database/migrations`.
- Laravel applications may also contain Inertia/React/Vite assets under `resources/`. Those files remain part of the Laravel application.
- `backend/bootstrap/app.php` can register API routes with a custom prefix, including **`apiPrefix: ''`**. The analyzer reads the configured prefix rather than assuming `/api`.
- Other ecosystems (Python, Ruby, Go, Rust, JVM, .NET, Swift/Xcode, C/C++ with CMake, Shopify themes) are detected from their manifests (`src/core/manifests.ts`): the application, its ecosystems and the frameworks its dependencies name. Their files are named by language, measured and highlighted, and TypeScript/JavaScript is analyzed in any application. Next.js/Laravel retain their existing framework analysis; Express/Nest add static registration packs. Python, Go, Ruby, Rust, Java, C# and Kotlin get Tree-sitter declaration extraction, including outside detected applications. Python adds static package/import resolution, lexical references/calls and initial FastAPI, Flask and Django registration packs; Go adds indexed module/workspace/package imports, recorded build contexts, bounded lexical/package references and calls, and initial net/http/Chi/Gin/Echo/Fiber/Gorilla Mux registration packs. Ruby adds original scoped syntax facts and literal source-load dependencies with recorded ordered load roots/cwd and runtime boundary diagnostics; Ruby adds scoped constants/direct methods and Rails/Zeitwerk autoload contracts; Rails adds initial source routing, resource expansion, original actions and callback references; Java/Kotlin add selected Maven/Gradle/configured roots, original imports, bounded scoped references/direct calls and initial Spring MVC and WebFlux registration/handler/path contracts; C# adds indexed MSBuild source compilations, scoped references/direct calls and logical partial types; ASP.NET adds initial serving-reachable minimal API registration/handler/path contracts; ASP.NET MVC and Rust resolution remain separate work.
- Analysis does not read credentials, connect to the application database, or invoke target application scripts. The index describes the working tree, with HEAD and dirty state recorded separately.
- The test fixture proves a login chain from page to table: page `/account` → `AccountPanel` → `handleSave` → `AccountService.signIn()` (base URL built in code) → `POST /auth/login` → `AuthController::login` → `AuthService::authenticate` → reads table `users` (Eloquent model `User`, `$table = 'users'`, declared by a migration).

## 2. Proposed architecture and location

Keep the tool in this separate workspace. It accepts a target repository path; default generated configuration/cache lives in `<target>/.codiluce/`, with `--state-dir` allowing all generated files to live outside that repository. No Laravel boot, Artisan invocation, database access, or application code mutation is required.

Use a TypeScript engine with these actual boundaries:

```text
src/core/       graph types, graph builder, identities, configuration
src/analyzers/ filesystem, Git metrics, TypeScript/Next.js (+ HTTP sites and wrappers), PHP/Laravel (+ migrations and models)
src/analysis/  capability/fact contracts, indexed sources/projects, language services, framework packs, isolated Tree-sitter extraction
grammars/      pinned WASM artifacts, owned declaration queries, provenance and licenses
src/pipeline/  ordered indexing, independent API matching, the bounded analysis cache
src/storage/   SQLite graph cache (transactions, bounded queries)
src/api/       HTTP inspection and projection API (reads only; on-demand history indexing when enabled)
src/cli.ts     init, index, inspect, serve, history
tests/         fixture repositories and integration tests
```

The future Next.js UI will consume query/projection APIs; neither analyzers nor storage depend on React. A graph is canonical; layout, LOD, selection, and source rendering are projections. No AI inference in the graph: language-model annotations (§21) live in their own store, beside the facts, and never change them.

## 3. Canonical graph schema

`SoftwareGraph` has a schema version, repository identity, entities, relations, diagnostics, and analysis-run metadata. Every entity and relation has nonempty evidence. Evidence has `source`, `confidence`, `analyzer`, `analyzerVersion`, optional repository-relative file, source range, commit, and explanation. Confidence does not replace provenance.

Entity types include repository, application, domain, directory, file, component, class, function, method, route, api_endpoint, controller, model, database_table, command, scheduled_task, external_service, test, and user_flow. Applications carry `frameworks` (configured, then declared by their manifests; the first, also `framework`, says what the application is), `ecosystems`, and `languages` (measured lines per code language, derived and excluded from the shape hash); their `language` is the one with the most lines. Hooks are functions with `role: hook`; Eloquent models (an `extends` chain reaching an Eloquent base) are `model`; tables declared by Laravel migrations are `database_table`, children of their application (§15). Each entity has `id`, `type`, `name`, optional path/language/parent/source range, metadata, and optional metrics. Relations include contains, imports, exports, calls, renders, references, routes_to, handles, requests, invokes, reads, writes, queries, maps_to, foreign_key, extends, implements, observed_call, part_of_flow, and changed_with. `invokes` points code or a scheduled task → the Artisan command it runs (a scheduled job → its handler). `reads`/`writes` point code → table, `maps_to` model → table, `foreign_key` table → referenced table (one relation per pair, every key column in metadata). `handles` points **endpoint → handler** consistently. `calls`, `renders` and `references` (a function passed as a value: an event handler, a callback) keep one relation per (from, to, type) with every site as evidence (up to 25) and `metadata.sites/lines/forms/events`. Symbols carry derived metadata: `callSites` (resolved, external, unresolved, unresolved names) and `effects` (category, operation, detail, line, status, target, the name matched on); both are excluded from the entity's shape hash, so their changes read as relationship changes, not as the entity changing.

IDs are hashes of repository namespace + entity identity, never absolute checkout paths or line numbers. Files initially use repository-relative paths. PHP symbols use application + fully qualified name + normalized parameter signature. TypeScript symbols use application + module-relative path + lexical qualified name + normalized parameter signature; module path is necessary because TS has module-scoped, not globally qualified, symbols. Signature changes change IDs. Symbols record declaration fingerprints (`contentHash` of the declaration text, `bodyHash` of the whitespace-normalized text after the name); history comparisons use them, with Git rename detection, for a separate lineage mapping that never rewrites canonical IDs (§13). Relation IDs use endpoints + relation kind + a semantic discriminator where needed; repeated references merge evidence.

Diagnostics are first-class records: analyzer, severity, code, file/line, `resolution: unresolved`, reason, and optional entity. TS/PHP parse failures are errors, are persisted, and produce a nonzero CLI status after successful cache writing. Structural syntax recovery and parser asset/lifetime failures are warnings with per-file partial/failed outcomes. Unresolved expressions never create invented edges.

Flows are derived, never stored: every flow is computed from the indexed relationships by the projection (§20); runtime traces, if ingested later, will be a separate overlay. There are no hand-made flows (§18). File metrics include Git history (`commits`, `authors`, `churn`, `lastChangedAt`, `lastCommit`) for the working-tree index (§17). Annotations contain provider/kind/value/confidence and never overwrite entity facts. Runs/snapshots include commit, dirty state, timestamp, config digest, schema version, and analyzer versions. Historical commits are stored as versioned snapshots in a separate store (§13).

## 4. Analyzer pipeline

1. Resolve and validate configuration; autodetect applications from their manifests without executing them (`manifests.ts`: an application, not only a workspace or tooling; nested applications are allowed, except inside a Next.js or Laravel application; a file belongs to the innermost one). Configured applications are completed from their manifests.
2. Scan sorted directories, prune ignored subtrees, create containment hierarchy and file metadata.
3. Read per-file Git metrics from one bounded `git log` (`git-metrics.ts`, working tree only, §17).
   Extract named declarations for the seven structural languages with lazy WASM grammars in a cancellable process. The manifest and query hash are part of cache/history identities; syntax recovery retains valid declarations with partial outcomes. Module/interface/struct/trait kinds use the existing `class` entity plus `declarationKind`/`role` metadata. See [grammar maintenance and supported subset](../grammars/README.md).
4. Discover Node projects from configured applications and indexed package manifests (`src/analysis/project-model.ts`). Build one TypeScript program per project over its own roots and indexed import dependencies (`src/analyzers/ts-program.ts`); declare owned symbols before binding exact source sites across programs. Resolve imports with the importing file's project options, find HTTP request sites and evaluate their URLs (`ts-http.ts`, `ts-url.ts`), resolve HTTP wrappers at owned call sites (§16), then resolve calls, renders and references with the project's type checker (`ts-references.ts`). After all ordinary declarations, `src/analysis/frameworks` runs pack declaration hooks inside the language cache unit. Express registers inline callbacks on their exact AST sites before HTTP effects and language references, while Nest binds bootstrap/module/controller registrations. Pack versions enter cache keys and run metadata. Compiler services can recover declaration ownership from cached graph entities for later packs. This runs before the `typescript-services-release` step: it releases compiler/checker instances before unrelated language work, while preserving lazy service reconstruction and project metadata.
5. Parse PHP with `php-parser`, collect namespaces/classes/methods, walk registered Laravel route files and statically evaluable includes/groups, replay migrations into tables and map models to them (`laravel-schema.ts`, §15), then resolve method calls, effects and table reads/writes (`php-references.ts`).
6. Independently match HTTP observations — literal URLs and URLs built from a proven base — to candidate endpoints. Compile the existing Next/Laravel path dialect once per endpoint and reuse request segments/eligible endpoint sets within a run (`src/analysis/routes/pattern.ts`). The versioned shared contract (`src/analysis/routes/contracts.ts`) adds Express syntax profiles, method sets, registration/mount proof, middleware and unresolved conditions. New dialects still require explicit adapters. `apiProxies` maps browser path prefixes to configured target applications with optional rewrites; server-relative or unknown-context requests to new framework endpoints stay unverified. Unmatched/ambiguous/unproven calls remain diagnostics.
7. Validate IDs, references, parents, evidence, confidence and containment cycles.
   Record per-file `metadata.analysis` outcomes for declarations, imports, references, framework behavior, effects and guards. Outcomes survive projection/history and appear in the inspector. Declaration-only files stay outside call/flow coverage.
8. Persist one generated snapshot atomically. Inspection queries load only bounded result sets.

Steps 4 and 5 are cached when indexing the working tree (§17): TypeScript uses a weak dependency component of projects, while PHP uses its Laravel applications. An isolated TS project keeps its own unit; connected projects invalidate together when a dependency changes.

## 5. Next.js extraction strategy

Recognize `app` or `src/app` route conventions. `page.tsx` creates a UI route; `layout.tsx` records its route scope; `route.ts` exposes endpoints only for exported HTTP methods. Strip route groups and parallel-slot segments, translate `[id]`, `[...slug]`, `[[...slug]]`, and diagnose unsupported intercepted route syntax. Store original filesystem segments so route inference can be explained.

Use AST nodes for imports/re-exports, exported symbols, functions, classes, methods, hooks, and JSX-producing functions/components. Source ranges and LOC come from parsed text. JSX output identifies components; capitalization alone does not prove a React component. File imports link to indexed local files; external imports are file metadata rather than unbounded external symbol expansion. Calls, renders and references are resolved by the type checker of the application's program (§14); the program sees only indexed files and the compiler's lib files, never `node_modules`.

Request sites are `fetch`, calls on the default import of `axios`, and calls on axios instances (`axios.create({ baseURL })`, local or imported). Literal URLs are matched as written; anything else is evaluated (§7), including through HTTP wrappers (§16). Methods are literal (or bound at a wrapper's call site) without dynamic option overrides. Local bindings/shadowed HTTP identifiers are excluded. Dynamic expressions, unresolved wrappers, unsupported axios forms, malformed files, and local imports that cannot resolve receive diagnostics. Exact asset imports (including Sass) use indexed paths and explicit tsconfig aliases when TypeScript's module resolver cannot resolve them. Relative literal paths can match same-application Next endpoints; cross-application relative URLs remain structural candidates until a proxy/origin is proven. Absolute URLs require explicit `apiOrigins` association. Queries are stripped for matching; segment parameters match literal segments; multiple matching endpoints remain ambiguous. No wildcard replacement of arbitrary JavaScript expressions.

Server-action directives and exports are recorded as metadata. A URL that is not literal is evaluated to a proven base (§7). Axios instances and wrapper functions are resolved (§16); `axios(config)`/`instance.request(config)`, instances held in class fields, the Pages Router and server-action call graphs are not.

## 7. Frontend/backend API matching

Collect HTTP request observations with caller entity, method, URL/expression, source range and resolution. The matcher is independent of analyzers and only creates `requests` when the method, path, origin association and route candidate are supported. Match each HTTP verb and ordered path segments; account for parameter names without asserting a dynamic URL is resolved. A known literal request matching conflicting web/API routes receives an ambiguity diagnostic. Preserve both request and route evidence on the edge. A relative URL that happens to match Laravel is insufficient to prove the frontend host forwards it: it receives `unverified-relative-api-boundary` instead. Next rewrite/proxy extraction is deferred.

Explicit `apiOrigins` can associate an origin such as `https://api.example.test` with the backend, and `apiOriginEnv` declares environment variables that hold an application's origin (a configured assumption, recorded as evidence). A non-literal URL is evaluated through templates, concatenation, `const` bindings, class properties (every assignment), local functions (every return, with argument binding), `new URL`, `.toString()`, `||`/`??` and conditionals into alternatives made of text, *holes* (dynamic values) and proven origins. Every alternative must reach the same application and path pattern; holes may fill whole path segments (matched only to route parameters; a literal route that could match them makes the request ambiguous) or sit after `?`. The proof's hops become evidence on the `requests` edge. Relative URLs from a Laravel application's own scripts reach that application (same origin).

## 8. Spatial and LOD strategy

Use deterministic hierarchical rectangles, initially ordered by stable IDs with fixed/persisted slots and bounded weights. Sort order alone guarantees repeatability, not insertion stability; persisted positions and localized subdivision address that separately. Layout is versioned outside the graph and never changes identities.

LOD 0: applications, with their Routes & endpoints and Database districts. LOD 1–2: directories (configured domains are not implemented). LOD 3: files. LOD 4: symbols. LOD 5: lazy source fragments. Start with native Canvas 2D, one React canvas component and an indexed hit-test structure; measure before adopting Pixi/WebGL. No React component per primitive. Hierarchy/viewport queries and aggregated selected-edge queries avoid sending the whole graph. Hierarchy is the default, selection exposes filtered incoming/outgoing edges, and breadcrumbs preserve context.

### Implemented visualizer (Phases 3–4, first iteration)

- **Location:** `web/` (Next.js App Router, React, TypeScript, statically exported and served by `codiluce serve`). ## 9. SQLite schema

Use built-in `node:sqlite` on Node >=22.12; npm scripts supply the experimental flag required by the installed runtime. Store schema version with `PRAGMA user_version` and reject unknown versions. Foreign keys are enabled. No Neo4j or separate DB server.

- `analysis_runs`: ID, repository ID/name, commit SHA, dirty state, analysis time, configuration digest, schema version and analyzer versions.
- `repository_snapshots`: snapshot/run/repository identity and commit; marks working-tree snapshots. Each successful index replaces the current generated graph transactionally; run headers survive. Full versioned entity history is deferred.
- `entities`: ID/type/name/path/language/parent, source range, metadata JSON; indexes on parent/type/path/name.
- `relations`: ID/from/to/type/metadata JSON; indexes on both endpoints/type.
- `evidence`: entity or relation owner, provenance JSON, indexed by owner; owner references enforced.
- `metrics`: entity FK and JSON metrics.
- `diagnostics`: analyzer, severity, code, file/line, entity, resolution/reason.
- Language-model annotations live in a separate database, `annotations.db` (§21); history in `history.db` (§13). Nothing else is stored.

Use a transaction for replace/validate/write: a failed index leaves the previous graph available. The cache can be deleted and regenerated. Inspection opens SQLite read-only. Source text is not stored wholesale; a future source endpoint must verify repository containment, indexed paths and bounded ranges before reading files.

## 10. Testing strategy

Node's test runner and TypeScript fixtures, plus Playwright browser tests (`web/e2e`). Fixture repository includes Next pages/groups/dynamic segments/layout/API handlers, JSX components, alias imports/re-exports, literal and dynamic HTTP calls, Laravel imports/groups/bootstrap/custom prefix/controller handlers, malformed code, ignored folders, and binary files.

Assert expected contains/imports/routes_to/handles/requests chains and exact evidence ranges; all dangling relationships/cycles/duplicate identities are rejected. Repeated runs and relocated checkouts must generate identical entity/relation IDs. Test transaction rollback, SQLite round trips, bounded search/hierarchy/neighborhood APIs, and config path constraints. Migrations (create/alter/rename/drop, conditional columns, both foreign-key forms, dynamic names), model mappings and table reads/writes; HTTP wrappers (axios instances, URL and method from parameters, nested wrappers, wrappers nobody calls); Git metrics across a rename; the analysis cache (replay equals a fresh index after PHP edits, TypeScript edits and new files; bounds; corrupt entries).

After each phase run `npm test`, `npm run typecheck`, `npm run build`, and index a representative target repository. No linter is introduced only for scaffolding. Target build/tests are not run because its application code is unchanged.

Small literal API matcher validates the separation early.

No instrumentation, cloud/collaboration or distributed indexing now.

## 12. Known limitations

No runtime behavior or live database schema is asserted: tables are what migrations declare. Working-tree scan includes untracked nonignored files and reports dirty state. No automatic domains. TypeScript caching follows connected project dependencies: one changed source re-analyzes its component, while unrelated project units can stay cached; any added or removed file invalidates the indexed path set. Scanner skips symlinks, secret-like files, generated outputs, large files and binary LOC with reasons. Each project gets one TypeScript program (parsed source files are cached per process by project/path/text, so history workers reparse only changed files); calls through callbacks, props, untyped values and interface dispatch stay unresolved and are counted, not linked. Project references are recorded for dependency invalidation; generated declaration outputs are not mapped back to source without an indexed import target. Workspace membership supports static npm/Yarn/pnpm path patterns, not arbitrary package-manager configuration code.

Middleware is drawn by name on request flows, not followed into its class; global middleware registered in bootstrap/app.php is not linked to endpoints (coverage counts middleware as framework configuration). Wayfinder route helpers (`@/routes`, `@/actions`, generated and Git-ignored) are not resolved: visits through them stay unresolved. Events and listeners, observers and notifications are not linked. Static Laravel extraction cannot prove registration inside arbitrary conditions/service providers, evaluate macros, or emulate resource transformations and route constraints. Migrations replayed are those in `database/migrations/*.php` (not package or custom paths); raw SQL, dynamic table names and unknown Blueprint macros are reported, not guessed; Eloquent relationships (`hasMany`…) and raw `DB::select` queries are not linked to tables. Diagnostics expose these gaps. TS detection does not resolve arbitrary metaprogramming; HTTP wrappers are followed through call sites the type checker resolves (not callbacks or wrappers stored in objects passed around). The live cache keeps one current snapshot; history lives in `history.db` (§13).

References: [TypeScript compiler API](https://github.com/microsoft/TypeScript/wiki/Using-the-Compiler-API), [PHP AST parser](https://github.com/glayzzle/php-parser), [installed Node SQLite API](https://nodejs.org/download/release/v22.12.0/docs/api/sqlite.html).

## 13. History

```text
Git commits (+ optional GitHub PR records)
      ↓  history index: materialize each commit from Git objects, run the same analyzers
Versioned snapshot store (history.db): content-addressed versions + per-snapshot membership
      ↓  snapshot sources (live codiluce.db, or a stored commit)
Snapshot-aware projection + diff (lineage, union with ghosts, timeline layout)
      ↓
Timeline / map / inspector diff / source diff
```

- **Store.** `entity_versions`, `relation_versions` and `diagnostic_versions` hold each distinct record once (keyed by a canonical-JSON hash; diagnostics by their content-derived ID); `snapshot_entities/relations/diagnostics` are integer membership rows. Entity versions also carry the columns the projection needs plus `content_key` (source hash, or size for unread files), `body_hash` and `shape_hash` (described facts without positions), so a snapshot loads without parsing JSON. A snapshot is one analysis run of one commit; `(commit, identity)` is unique, where identity digests the written configuration, analyzer and schema versions and the application policy.
- **Revisions.** `TreeMirror` writes a commit's tree into a scratch directory from `git diff-tree` and `git cat-file --batch`, then applies only the next commit's difference (symlinks as symlinks, submodules as empty directories). The filesystem analyzer skips the ignored-file inventory there (only tracked files exist). Configured applications missing at a revision are matched to the single autodetected application of the same kind (primary framework, else ecosystem), keeping the configured name so symbol identities continue. Workers are child processes over contiguous commit ranges; the parent owns the store.
- **Diff.** `computeDiff(baseline, target, renames)` classifies through lineage: `added`, `removed` (ghost, re-parented into union IDs), `moved` (renamed or reparented, including a changed path), `modified` (source, described facts, signature, kind, size) or `unchanged` with `relations`/`diagnostics` facets. Relations compare by mapped `(from, to, type)` (analyzers use no discriminators); diagnostics by code, severity, owner, mapped file and reason, ignoring lines.
- **Lineage.** Git renames (files), directory renames implied by them (path-suffix votes), symbols by type + qualified name under the mapped parent (or anywhere when PHP-qualified or body-confirmed), by unique name-independent body fingerprint, and remaining entities by type + name under the mapped parent, pairing equal same-named groups in source order.
- **Layout.** The live view keeps `layout.json`. History views use a timeline registry built at index time (per container, every child slot in first-appearance order; per slot, the largest weight; aliases from consecutive-commit lineage) and packed once; snapshots are placed in those slots, containers shrink to their current extent. Snapshots outside the registry (e.g. the working tree) extend it in memory.
- **Split view.** Comparisons show an overview of the whole repository and one view per place that changed (`projection/regions.ts`, shared by the server and the browser). Each changed entity is anchored at its *unit*: its file, or the area holding it (routes, tables and commands in their district); an area that changed itself counts through the changes inside it when there are some. A place's view frames the bounding box of its changed units. `auto` narrows the root to the smallest area holding every change and splits greedily: places whose typical changed unit would span less than a tenth of their view first (most changes first), then the loosest (box area over the parts' box areas); within the first page (5 views) a split must bring the views ≥1.5× closer by area, beyond it only unreadable places split, and the repository itself always splits. Fixed levels anchor each unit at its application, folder or itself. The browser groups time-lapse frames with the same code (a frame equals the settled comparison of its commit), and while playing groups the frames due before the next update. Each view is a `MapController` with role `region` (own camera, smaller open threshold); the overview (role `overview`) runs the clocks and draws the views' visible plane rectangles; a coordinator is the store's navigator while the split is shown.
- **Source.** Commit snapshots read the Git blob of the indexed file at their own commit (`ls-tree` validation: regular file, size bound), and diffs run Myers' algorithm on the two versions (symbol ranges or whole files), bounded in edit distance and output size.

## 14. Calls, blast radius and steps

```text
analyzers: calls / renders / references (+ evidence per site), callSites, effects
      ↓  projection index (any snapshot or comparison)
impact.ts  — dependents, hop by hop            steps.ts — what an anchor sets in motion        request-flows.ts — one request, end to end
      ↓                                              ↓  conditions.ts (source of the viewed snapshot)       ↓
Impact view + map overlay, commit reach        Flow view: outline / diagram, map highlight     Flows list, Flow view: lanes, map trace
```

- **Call resolution.** An edge exists only when a site resolves to a declaration that is an indexed entity. TypeScript uses `getResolvedSignature`/symbols of the application's program, following aliases, `useCallback`-wrapped functions, class fields holding functions, properties of objects returned by hooks (`const { logout } = useAuth()`), and methods of values held in `useMemo(() => X.getInstance(), deps)`: React's types are not in the program, so such a value is typed from the factory's return expression. PHP types receivers from declarations only (see §6). Sites that reach lib globals, packages or framework classes count as external; callback parameters, props, untyped values and interface dispatch count as unresolved, with the called names. Name-only matching never creates an edge.
- **Effects** are matched on resolved names, never on text alone: an imported facade class or its global alias, a class whose `extends` chain reaches an Eloquent base, a lib global (`localStorage`, `window.location`, `Response`), an import from the framework (`next/navigation`, `next/server`). Responses carry literal statuses (`abort(404)`, `response()->json($x, 201)`, framework exceptions, FormRequest validation 422, implicit controller returns 200).
- **Blast radius** (`impact.ts`). Every relation reads "from depends on to", so dependents are the `from` side of incoming relations. Symbols and tables follow symbol-level types (calls, renders, references, handles, routes_to, requests, extends, implements, reads, writes, maps_to, foreign_key), files follow imports and re-exports; containment is not climbed; a container seeds everything inside it. Breadth-first by hop count, bounded by depth (≤10) and 5,000 entities, first-reach relation kept per entity for the chain. A comparison seeds the entities the target modified (own facets: source, definition, signature, type, size) or removed, files only when no symbol inside them changed, and also walks relations removed since the baseline. Unknowns are reported: unresolved HTTP findings when an endpoint is reached, and unresolved call sites whose called name equals a seed's name.
- **Steps** (`steps.ts`). Forward over routes_to, renders, calls, references, requests and handles. A node is a step when it is the anchor, a page route, an endpoint, an endpoint's handler, a trigger (reached by a handler reference or a call carrying an event), or an action (effects or outgoing requests); effects are steps of their own (network effects already linked to an endpoint are drawn as the endpoint). Other nodes are folded into the link (`via`, each with its spatial ancestors). Nothing is capped: every reachable step is drawn once, the walk ending because each entity becomes a step at most once (a page reaches ~600 steps on Etengabe, in ~350 ms). What a step leads to is ordered by fold depth, then file and line. Navigation is the one boundary: an endpoint serving another page (`pageEndpoints`), reached by a request, is a step marked `navigation` and not followed. Links carry the relation chain; the service adds each hop's first site line and the guards there.
- **Conditions** (`conditions.ts`) are read at request time from the snapshot's own source (Git blob for commits), from the node at the site line (hinted by the called name) up to the owner's boundary: `if`/`else`, ternaries, `&&`/`||`, `switch` cases, `catch`, and early exits in enclosing blocks. Nothing is stored; an unparseable file gives no guards.
- **Request flows** (`request-flows.ts`). One per endpoint — the entity both sides of a request share — plus one per entity whose requests no endpoint answers (entities with HTTP findings). Inbound, backwards from the endpoint: `requests` to every caller, then incoming calls, references, renders and routes_to up to every page route reached (or the outermost callers when none is); the event relation closest to the caller makes its target the *trigger*, everything else is folded into the links. Server side: the endpoint's `middleware` names (not followed into classes), a FormRequest's validation as a gate with its 422 exit, then forwards from the handler over calls and references, as deep as they go. Nothing is capped: each entity is drawn once, which ends every walk (on Etengabe the largest flow, `POST /lessons/start`, has 237 nodes — its caller sits in a component every page renders, so all 16 pages are entries — and all 267 flows are listed in ~0.5 s). Callables are laned by their class: the handler's own class and controllers, models, everything else is a service; lanes only move forward along a call and deeper calls take the next sub-column (3 per lane). Effects become responses (by status), models and their tables (Eloquent target and `maps_to`), or other side effects; reads/writes relations add tables the effects did not name. *Back on the client*: the caller receives every response, then its effects after the request's line — and, up the chain while it is made of calls, each caller's effects after its call — by source order. Whatever cannot be seen is a gap node: a caller nothing indexed calls, an endpoint no indexed code requests, a closure or missing handler, no classified response, unresolved call sites (with their names), a request no endpoint matches (with the finding's reason). Status: *complete* (a page or event reaches the call, a handler and a response, no gaps), *partial*, *headless* (no indexed caller) or *unmatched*. Flows are built per view on first request and cached with it (Etengabe: 267 flows listed in ~0.5 s, the largest drawn in ~70 ms); the detail adds entity summaries, the folded entities, every hop's relation (Why?) and the conditions at each site.

## 15. Database tables from migrations

```text
database/migrations/*.php (filename order, up() only)
      ↓  Schema::create / table / rename / drop(IfExists), optionally through Schema::connection()
      ↓  Blueprint closure: columns (+ modifiers), change(), renameColumn, dropColumn, morphs, timestamps, foreign keys
tables (database_table, child of the application)  ← maps_to ← models (explicit $table, else convention)
      ↑ foreign_key (table → referenced table)       ↑ reads / writes ← methods (Eloquent statics, instances, DB::table('…'))
```

- **Replay** (`laravel-schema.ts`). Migrations run in filename order, as Laravel runs them; only `up()` is read. The facade must resolve to `Illuminate\Support\Facades\Schema` (or the global alias). A table is the result of every operation on it: created, altered (columns added, changed, renamed, dropped), renamed (`previousNames`), or dropped (gone). Columns under a condition (`if (!Schema::hasColumn(…))`) are kept and the table is marked `conditional`. A table that migrations only alter is still declared, with a `table-created-elsewhere` finding. Non-literal names, raw SQL and Blueprint calls the extraction does not know are findings, never guesses.
- **Entities.** `database_table` with ID `(application, table name)`, path and source range of the migration call that created it (or first altered it), metadata `columns` (name, type, nullable, unique, primary, default), `foreignKeys`, `migrations`, `origin` and `connection`; each migration operation is evidence (framework source, explained as the intended schema, not the live database). The projection places tables in a **Database** district of their application.
- **Foreign keys.** `foreignId('x_id')->constrained()` (table guessed by the framework convention, and said so), `constrained('table')`, `foreign('col')->references('id')->on('table')`, `foreignIdFor(Model::class)`; `dropForeign` removes them. A key to a table no indexed migration declares is a finding.
- **Models.** Classes whose `extends` chain reaches an Eloquent base become `model` entities. They map (`maps_to`) to the table of their `$table` property (own or inherited from an indexed parent; php evidence), else to Laravel's convention (snake case, plural of the last word; framework evidence). A model overriding `getTable()` or setting `$table` dynamically is not mapped; a mapping to a table no migration declares is a finding.
- **Reads and writes.** Eloquent effects (§14) become `reads`/`writes` relations from the method to the model's table (statics such as `User::where(…)->first()`, instance writes such as `$user->update(…)`), and `DB::table('literal')` reaches the named table. Blast radius follows them, so a table's dependents are the code that reads or writes it, the models mapping to it, the tables referencing it, and everything that depends on those.

## 16. HTTP wrappers

- **Sites** (`ts-http.ts`): `fetch(url, init)`, `axios.<verb>(url, …)` on the default import, and `<instance>.<verb>(url, …)` where the instance is a `const` initialized by `axios.create(config)` from `axios` (in any module). An instance's `baseURL` and the request path are joined as axios joins them (one slash), unless the path is absolute.
- **Wrappers.** When a site cannot be resolved only because its URL or method depends on parameters of the function around it (the evaluator reports the unbound parameter, `ts-url.ts`), that function is a wrapper. Each of its call sites resolved by the type checker is evaluated again with the parameters bound to the arguments (omitted ones to their defaults, or missing); when that call site is itself inside a wrapper, the walk continues outward (at most four levels, 300 call sites per wrapper). Methods are read from `init` objects, through spreads of bound arguments (`{ ...init }`), later keys winning.
- **Results.** A resolved call site is a request of its caller (`requests` relation, a network effect on the caller saying through which wrapper), with evidence: the call site, the wrapper's site, every intermediate call and the URL's proof. The wrapper's own network effect is marked `wrapper` (Steps does not draw it) and an `http-wrapper` finding counts its call sites. A call site that does not resolve is an `unresolved-http-call` on its caller; a wrapper nobody calls stays one on the wrapper.

## 17. Git metrics and the analysis cache

- **Git metrics** (`git-metrics.ts`). One streamed `git log --no-merges -M --numstat -z --relative` over the newest 10,000 commits of HEAD, newest first. Renames are followed (older history under an old path is credited to the file's current path). Per file: commits, distinct authors (e-mail, compared case-insensitively), churn (lines added + deleted), last change date and commit. Merge commits are not counted; uncommitted edits are not in them; a file never committed has none (`not measured`). Truncation and an unreadable repository are info findings. History snapshots skip this analyzer.
- **Analysis cache** (`src/pipeline/cache.ts`, `<state>/cache/`). The unit is one analyzer over its dependency scope (TypeScript: a weak component of projects; PHP: every Laravel application together; Python imports: an initial repository-wide unit; Git metrics: per HEAD; structure: reusable per-file facts). Its key digests what the analyzer reads: source paths and content hashes, the repository's indexed path set, package/config inputs including inherited configuration, the configuration, compiler options and analyzer/schema versions. A miss records what the analyzer did to the graph (entities, relations, diagnostics added; evidence merged; metadata and metrics keys set on existing entities; HTTP observations with the effect each one updates) and a hit replays it, only if it applies cleanly. Entries are gzip JSON, at most two per unit and 256 MB in total, oldest first out; corrupt entries are misses; the directory can be deleted any time. `index --no-cache` re-analyzes everything; history indexing never uses it.

## 18. Hand-made flows (removed)

Earlier versions let a person record a named flow (entities clicked in order, *declared*) or fill one with the shortest chain of relationships between two entities (*static*), stored in `<state>/flows.db` with write routes under `/api/flows`. Both were removed once every flow became derived (§20): a page, a request, a command or a scheduled task already yields its flow from the index, with real links, completeness and gaps, while a hand-made sequence said nothing the index could check and went stale after reindexing. The server has no flow writes and no path query; a `flows.db` left by an earlier version is ignored and can be deleted. Runtime traces, if ingested later, are the place for observed sequences.

## 19. Entry points without HTTP, and Inertia

- **Commands** (`src/analyzers/laravel-console.ts`). A class whose `extends` chain reaches Laravel's console `Command` and names itself literally (`$signature`, first word; `$name`; `#[AsCommand(name:)]`) is a `command` entity, child of its application (a **Console** district on the map), `handles` → its `handle()` (or `__invoke()`). `Artisan::command('name', fn)` in a console route file is a closure command. Commands named at runtime are info findings.
- **Scheduler.** Console route files (`withRouting(commands:)`, else `routes/console.php` by convention), `withSchedule(fn (Schedule $s) => …)` in bootstrap/app.php and the console Kernel's `schedule()` are read for `Schedule::command/job/call/exec(…)` chains: a `scheduled_task` entity per call (identity: verb, target text, cadence, occurrence — never a line), its cadence from the frequency methods (`everyThreeHours`, `dailyAt('02:00')`, `cron('…')`) and the rest as modifiers, `invokes` → the command (by command line or class constant) or the job's handler. A target that is not indexed is a finding.
- **Running commands by name.** `Artisan::call/queue/callSilently('name …')` and `$this->call('name')` inside a command are `invokes` relations (form `artisan`) to the command; a computed name is an `unresolved-artisan-call` finding. `Job::dispatch()` and `dispatch(new Job)` are calls of the job's `handle()` (form `dispatch`).
- **Inertia, server side.** `Inertia::render('page', …)` (the `Inertia\Inertia` facade) and `inertia('page')` are `response` effects with operation `inertia`, status 200 and the page name (not also a generic return value); a route closure rendering a page records `inertiaPage` on its endpoint. `src/pipeline/inertia-linker.ts` runs after both language analyzers (uncached: it only joins their results) and relates the method or endpoint to the page's default export (else the file) under `resources/js/pages` or `Pages`, with `renders`; a missing page is an `inertia-page-not-found` finding.
- **Inertia, client side** (`src/analyzers/ts-http.ts`). Calls on `router` from `@inertiajs/*` (`get/post/put/patch/delete`, `visit` with the method from its options), on a `useForm()` form (assigned, or a destructured `post`), and the `<Link href method>` / `<Form action method>` elements are request sites like `fetch`; relative URLs from the Laravel application's own scripts reach it (same origin). A link or form whose URL is not proven is recorded on its file, without a finding (navigation menus built from data are common).
- **Next.js wrappers.** A page route `routes_to` the default export of every `layout`/`template` above it and its `loading`/`error`/`not-found` files (`linkNextWrappers` in `typescript.ts`), so components rendered only by layouts are part of the pages they wrap. File entities record `defaultExport`.
- **Request flows** follow `handles` backwards from a handler that renders a page, so the endpoint serving an Inertia page is the entry of the requests that page makes (a HEAD twin is skipped), draw the rendered page back on the client after an Inertia response, and have console counterparts: `commandFlow` (what runs the command: scheduled tasks, code by name — with its own client chain — or *run by hand*; the command; its handler and what it reaches) and `scheduleFlow` (cadence → command or job → handler).

## 20. Flow catalog and coverage

```text
entry points (page routes, endpoints, commands, scheduled tasks, unmatched callers)
      ↓  catalog.ts: forward slice per entry (+ the request picture's own entities)
flows: kind, summary, members (entities), files     →  entity → flows index (also for areas)
      ↓  computeCoverage
a category per file, counts per area                →  Coverage lens, inspector "Flows", Flows panel
```

- **Kinds.** `page`: a Next.js page route (drawn by Steps), or a GET endpoint whose handler (or closure) renders a client component (an Inertia page, drawn in lanes). `request`: every other endpoint (a HEAD route mirroring a GET is listed once). `command`, `schedule`, `unmatched` (an entity making requests no endpoint answers).
- **Slice** (`forwardSlice`): breadth-first from the entry over routes_to, renders, calls, references, requests, handles, invokes, reads and writes, bounded at 6,000 entities (flagged when reached). A `requests` edge into another page's endpoint is navigation: the endpoint is included, not followed, so one page's journey does not contain every page it links to. Models mapping a reached table are added. The members of a flow are its slice plus the entities of its request picture (callers and their entries). Built once per view (Etengabe: 346 flows in ~0.75 s).
- **Coverage** (`computeCoverage`), per file, in order: `asset` (not code: not one of `CODE_LANGUAGES`), `entry` (it defines an entry point: a page file, a route file, a command class, the console routes), `flow` (a member of at least one flow), `unanalyzed` (code whose calls no analyzer resolves — a language other than TypeScript, JavaScript and PHP, or PHP in an application that is not Laravel — unless code in a flow imports it), `test` (tests, `__tests__`, e2e, seeders, factories), `supporting` (imported, re-exported, extended or implemented by a file in a flow; or a migration declaring a table a flow reaches), `config` (config, bootstrap, `*.config.*`, migrations no flow reaches, middleware/providers/kernels/exception handlers), `outside` (not in a configured application), `explained` (an unresolved call site calls one of its symbols by name; a command while some command is run by a computed name), else `unreached` — with a reason naming the files that use it when only unreached code does. Areas count the categories of the code files below them; `asset` and `unanalyzed` are not measured (no flow can reach them), so they stay out of the share of code in flows.
- **Relationships of a file** (`relations(id, { scope: 'contained' })`): the file's own and those of its symbols that cross the file's boundary, each with the symbol inside; relations between two symbols of the file are left out.
- **On the map** (`web/lib/map-flow.ts`, `controller.ts`, `renderer.ts`): every flow (lanes, Steps) becomes stops (an entity is one stop), edges between them (lanes: carried through nodes without an entity, so an endpoint links to its handler past its middleware; the way back — `returns`, `then` — marked), pins for nodes that are not entities, each shown once the stop it hangs from is reached, and *members*: every entity it touches, folded ones included. Members and their ancestors stay lit; the renderer dims the rest. `branchesOf` splits a flow into branches: with one starting stop (no incoming forward edge), each stop it leads to directly; with several, each start. A request is split by where it is made from instead (`requestBranches`): for a page, opening it directly first (the server, then the page it renders); then one branch per caller and each choice leading to it on the client, grouped by origin (*From this page*, another page, the scheduler, no indexed trigger). A branch plays only its own choice on the client, then the server; the page a response renders comes once the server is done, the way back to the caller last. An Inertia page entered through the endpoint serving it carries the component that endpoint renders (`page` on the client node), and is drawn there rather than on the endpoint, so a page requesting itself (filters, sorting) is a loop through the server, not one stop mixing its controls with the controller. A branch's waves are breadth-first over forward edges from its start; each edge flows in the wave of its source, the way back in a last wave. Playback (`playback.ts`) runs over branches, a branch lasting one wave per edge step plus one (`WAVE_MS`); the renderer draws each link of the branch as a faint track, and the part the pulse has reached as a glowing line with dashes streaming toward the target (still while paused or with reduced motion), brightest at its front. `Scene.visible` opens the areas of the current branch whatever their size; callouts carry the wave number (siblings share it). A selection made by the user pauses playback.

## 21. Language-model annotations

```text
index (+ history)  →  tasks.ts: requests per task (items, content keys)  →  runner.ts: estimate → pilot → run (budget)
                                                                              ↓  OpenAI Responses API, strict JSON schema
annotations.db (kind, target, content_key, prompt_version, model, value, ste)  →  projection: titles, summaries, domains, notes
```

- **Store** (`src/ai/store.ts`): `<state>/annotations.db`, separate from the regenerated graph cache; an annotation is keyed by what it describes (`file` → file ID, `folder` → directory or application ID, `flow` → entry ID, `commit` → SHA, `domains`/`overview`/`chapters` → `repository`) and records the digest of its request text, the prompt version, the model, the value and its ASD-STE100 score. An item is sent again only when its request text or the prompt version changes (`--force` overrides). Runs record tokens, cost and the estimate. File annotations keep the file's content hash, so a description of a file changed since is flagged.
- **Tasks** (`src/ai/tasks.ts`), in order: `files` (low tier; per file: path, language, lines, flows touching it, entry points, symbols, effects and table access, what it requests, runs, renders and calls, what uses it, and the first ~3 KB of source; 6 per request), `flows` (low; the request picture's entries, triggers, callers, services, tables and responses, or a page's components, endpoints and effects; 15 per request), `commits` (low; message and the comparison with the previous indexed commit: files, entities by status and type, symbols before files, relationships, routes and endpoints; 6 per request), `folders` (low; their files' descriptions), `domains`, `overview`, `chapters` (high; one request each, over the folders' descriptions, the flows, the domains, and the commits' notes). Batched answers are matched back by key; unknown and duplicate keys are dropped.
- **Models and cost** (`src/ai/pricing.ts`, `src/ai/openai.ts`): `gpt-6-luna` at low reasoning effort and `gpt-6.1-sol` at high effort through the Responses API (strict JSON Schema; retries on 429/5xx; refusals and incomplete answers are errors). The estimate prices every pending request from its characters (~3.4 per token) and an output allowance per item plus reasoning per request; the pilot sends the first request of each small task and replaces those guesses with measured tokens. The command refuses to run above `--max-cost` (also when the unmeasured estimate is over three times it), and the runner stops starting requests once the spend reaches it.
- **ASD-STE100** (`src/ai/ste.ts`): every request carries the same writing rules (short sentences, active voice, simple present, no -ing forms or contractions, approved words, names from the code as they are, facts from the input only); every prose answer is scored on the rules a program can test: at most 25 words per sentence (20 better), no passive voice, no -ing forms, no contractions, no word from a list of common unapproved words, at most six sentences per paragraph; code identifiers, paths and quoted names are technical names and are skipped. On Etengabe the mean scores are 98–100% per task (target 80%; the lowest single description 71%).
- **Domains** (`src/ai/domains.ts`): the model names 6–16 domains with the paths they include (`platform`: only folders every domain uses). Every file takes the longest matching path; a file no path matches takes the domain its connected files clearly agree on (imports, calls, renders, requests, handles, table access; each neighbour weighted 1/log2(2 + its degree), a 60% share needed), over rounds; what stays undecided is `platform`; a file matched only by a `platform` path moves to a domain that holds a clear majority of at least two of its connections. Endpoints follow their handler, page routes their component, commands their handler, tables the code reading or writing them, scheduled tasks their command. Recomputed when the rules or the index change.
- **Features panel** (`ProjectionService.features`, `/api/projection/features`): the domains with code files in the view, largest first and `platform` last, each with the folders directly holding its code files; the feature of every file and entry point (symbols take their file's) and code files per feature in each area. Domains are assigned on the live index; entity IDs are stable, so a history view keeps the features of what still exists. Flow summaries carry `feature`, the domain of their entry point: a flow belongs to the feature where it starts, so a feature lists the flows it starts, not every flow passing through it. The client lists features as a collapsible tree (feature → description, flows, folders) in the left panel; focusing one dims what lies outside it on the folder map (the same lit rule as a family in focus, from `of` and `areas`), badges closed areas with its file count, and frames its folders. Feature and family focus replace each other; a playing flow wins over both.
- **The middle of the screen** (`web/components/Workbench.tsx`, 2026-10-08). The map is the overview; the tools that answer day-to-day questions open in the middle as tabs beside it: the **Flow view** (`FlowView.tsx`: one subject — a request, command, task, page or any code that runs — drawn in lanes when it is a request, command or task and in layers otherwise, or as the outline of its steps; the lanes come from `/request-flows/:id`, the layers and outline from `/steps/:id`), the **Impact view** (`ImpactView.tsx`: the blast radius of an entity or of the uncommitted changes, pinned to its origin, by hops or grouped by application, feature or folder server-side) and the **Files view** (`FilesView.tsx`: the files a feature, a data family, a coverage category or a person lights, from `/api/projection/files`). The store keeps which one is in the middle (`center`); the canvas stays mounted and shrinks to a corner, where the controller fits the whole repository with a coarser level of detail (`CORNER_LOD`), keeps the camera it had, defers flights and fits until the map is back, and draws only what the tool in the middle lights. Search results carry the same entries (on map, lanes, what happens, impact). Why: day-to-day questions are answered through lists, lanes and focused graphs; the map orients.
- **Uncommitted changes as an origin** (`ProjectionService.workingImpact`, `/api/projection/impact-working`): when History has the commit the live index was taken at, the walk starts from what changed since it (the comparison seeds); otherwise from every entity in the files `git diff --name-only HEAD` and untracked files report, which over-approximates (a file's dependents count even where the change did not touch what they use). Changed paths without a file in the index (deleted, not analyzed) are counted.
- **Removed: the Features view** (2026-10-08). The live map used to be redrawn by domain (`lens=domains`: repository → domain → folder → file). It was replaced by the panel: one map, arranged by folder, with features lit on it.
- **Serving**: flow summaries carry `title`, `goal`, `actor`; `/api/annotations` the overview, domains and cost; `/api/annotations/entity/:id` an entity's description, role and domain; the timeline its commits' notes and the chapters. Without `annotations.db` nothing changes.

## 22. Data families

Grouping that needs no language model (`src/projection/families.ts`, pure and deterministic).

- **Data families** (`dataFamilies`): tables are joined by their foreign keys (union-find), except through a *hub* (a table linked to six or more tables), which is a family of its own; a table named after another one (the longest `prefix`, `prefixs`, `prefixes` or `prefix`→`ies` that names a table) joins it, unless that table is a hub, which it joins only when nothing else connects it; tables sharing a first word of three letters or more that names no table join each other. A family is named by its hub, else the table most tables are named after, the most linked, the most used, the shortest name; tables all sharing a prefix of three letters or less are named by it in capitals (`CRM`). Files are placed by the tables their own code touches (through `fileResolver`: maps_to 4, a migration creating or changing the table 4 — the table's `migrations` on the live index, its own path otherwise — writes 2, reads 1; a hub's family counts half). The rest follow connected code over rounds applied together (order-independent): a file joins the family holding ≥60% of the weighted code it uses (each file weighted 1/log2(2 + its links), half for a hub's family; code only it uses is ignored, other code without a family counts half against the majority), or the family of every file using it when they all agree. Endpoints, routes, commands bridge their callers to what they run (a request links the caller's file to the handler's), and follow what they run; scheduled tasks follow their command. On Etengabe: 24 families, and 365 of 914 code files in one (Commands 55 of its 57, migrations 98 of 101). Most frontend files have no family: their requests go through a wrapper the analyzers do not resolve.
- **Serving**: `/api/projection/families` serves a view's families, each entity's, and files per family in each area (code without one as `none`). History views always show folders; families can still color them.
- **Client**: the families overlay colors files (symbols by their file), entry points and tables, badges closed areas, and dims what lies outside the family in focus (or outside *No tables*); the focus wins over the selection's highlights, a playing flow over both. The inspector of a folder, application or repository shows its code files per family from the same response (`areas`), loaded without coloring the map; selecting a family focuses it. Families and coverage both color files and replace each other.
- **Removed: the Data view** (2026-10-08). `lens=data` redrew the live map by family (repository → family → folder → file); the overlay and the inspector's breakdown answer the same questions on the folder map.
- **Removed: Group files** (2026-10-08). The files of large folders were drawn in groups inside them (by data family or by the first word of their names). Groups made those folders larger, which moved the whole map, and on Etengabe they reached six folders; the inspector's breakdown answers the same question ("what are these 55 commands about?") without changing the layout.

## 23. People: who changed which code

- **Server** (`src/history/authors.ts`): one `git log --topo-order -M --numstat` per commit shown, newest first and children before parents, merges included for ancestry (`AuthorLogs`, kept per head; the live index's in `<state>/authors.json`). `AuthorHistory` resolves people once per log: union-find over identities by address (case-insensitive; GitHub no-reply by login) and full name (two words or more), never across kinds, so an agent committing under a human's address (aider's `Name (aider)`) stays apart. Kinds come from names and addresses (`kindOf`). `order` is a person's rank by first commit, so colors stay the same in every window. `fold(anchor)` walks the commits reachable from the anchor and credits every change to the path its file has there (renames followed newest first), leaving out merges and commits that changed nothing under the indexed root.
- **Projection** (`src/projection/authorship.ts`, pure): a window filters the folded commits by author date (`365d`/`90d`/`30d` up to the anchor's commit date) or, while comparing, drops what the baseline could reach (`range`). Per file and person: commits, lines added plus deleted, lines in commits they authored; the *main* person of a file has the most authored lines, then lines, commits, latest change. `authorshipResult` (people, main person per file and entry point, files per main person per area with `none`), `personAuthorship` (files, entries, areas, folders, latest 60 commits, every SHA in the window for the timeline) and `entityAuthorship` (a file; a symbol's or entry point's file; every file of an area or district) are cached per view and window. No language model is involved; a later model layer can name what people work on from the same figures.
- **Client**: a `people` store slice (window kept in preferences; colors, focus and the focused person's detail stamped by view and window); the renderer reuses the family overlay for both the colors (`people`) and the focus (`person`); the People panel, inspector sections, map legends and the timeline marks read the same state. Coverage, data families and people color files one at a time; a lit feature, family or person lets the others go.
