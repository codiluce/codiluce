03 / INTENT & BEHAVIOR

Use context where needed

LLMs can suggest responsibilities, architectural roles, and explanations. Human declarations, contracts, tests, and runtime evidence are better inputs for claims about domain boundaries or behavioral correctness.

The strongest first feature would be a Design view: architecture roles on the existing map, a focused dependency diagram, and an evidence inspector. Start with boundaries, cycles, DI, and a configured ports-and-adapters view. This is a product recommendation from the source inspection and research, not a measured implementation estimate.

Show roles, boundaries, and the evidence between them

Keep the repository map as the navigation surface. Architecture is an additional grouping and relationship view: a file may participate in several patterns, and an architectural module may span several folders. Preserve canonical file containment and use overlays or projection groups for those memberships.

On the map

Color regions by declared domain/application/infrastructure roles. Add a small pattern badge only at a useful zoom level. Select a badge to reveal its participants; outline violating dependencies and dim unrelated code.

In a focused diagram

Draw ports and their adapters, DI consumers and bindings, Strategy alternatives, Factory products, or Observer fan-out. Label every edge by what it means. Offer a dependency matrix for large module graphs.

In the inspector

Show the role, supporting source locations, detector or declaration, scope, unresolved prerequisites, and alternatives. Offer “confirm,” “exclude,” or “declare role.” A manual declaration records intent; it does not prove implementation compliance.

Use solid edges for source-backed facts, dashed edges for candidates, explicit labels for configured bindings, and a separate runtime mode for observations. Show “declared role,” “structural match,” “candidate,” and “unresolved” as text as well as color. Avoid a single “SOLID percentage,” a fixed six-port hexagon, or a pattern count presented as a quality score.

Concrete map interaction proposal

Add a Design entry with three local overlay modes: Architecture shows declared role tints and boundary labels; Patterns selects one instance and highlights its participants with their roles; Rules reveals a specific forbidden dependency and the source witness. The existing Inspector holds the selected instance, participant list, provenance, and source evidence. Selecting any participant locates its existing building. These overlays preserve code positions and file-type shapes.

At repository zoom, show module role summaries and counts of relevant instances or findings. At file zoom, show a compact pattern-membership badge only where it is useful. At symbol zoom, reveal the actual consumer, contract, provider, factory method, or delegated operation. Do not put every pattern edge on the full repository map at once. When architectural membership spans unrelated folders, tint their existing footprints or show a grouped projection on request; do not move canonical files merely to make a contiguous district. SOLID appears as individual evidence-backed checks or explicitly labeled review suggestions.

C4 offers a useful hierarchy for the architecture zoom levels, but a repository tree is not automatically a C4 system/container model. Runtime containers, deployment boundaries, and external systems require declarations or deployment evidence. C4 model.

Basic and advanced patterns: feasibility catalog

This is a representative product-oriented survey, including all 23 GoF patterns. There is no finite universal catalog of every design technique. Every row is visually representable; the assessment concerns how safely Codiluce could identify or check it. These are proposed detectors, not a list of shipped capabilities. Pattern names and families follow the original GoF catalog; the detection and visual assessments are this report's engineering judgments.

D · Deterministic Bounded facts or explicit rules

C · Candidate Repeatable structural recognition; intent ambiguous

H · Context Human intent, contracts, or optional LLM

R · Runtime / proof Behavioral guarantee needs more evidence

D does not mean universal completeness. It assumes required language facts, configuration, and framework subset are supported. C can be implemented entirely without an LLM. R does not mean formal verification is always impossible; explicit specifications and restricted programs can make particular properties provable.

What “deterministic” can honestly mean

LayerCredible resultWhat it does not establish
Extraction“This source location declares a dependency on token T,” with the resolution chain and conditions.Which runtime override wins in every environment, or whether the call executes.
Recognition“These participants satisfy version 2 of our Strategy-shaped predicate.” Same inputs and versions produce the same match.That Strategy was the author's intent or is the best interpretation.
Conformance“This known domain symbol imports this known infrastructure symbol, contradicting declared rule R.”That no violation exists in unanalyzed files, dynamic code, external modules, or omitted edge classes.
Behavior“This test/trace demonstrates this execution,” or “this formal contract holds under these modeled assumptions.”That unobserved behaviors, all failures, and all production schedules satisfy the same property.

Reproducibility is not correctness. Pin the source snapshot (including dirty-tree hashes), compiler/build selection, language/framework versions, detector version, rule configuration, and input ordering. Stable participant IDs and canonical sorting allow cached results and repeatable diagrams. Dynamic resolution and budget exhaustion must produce explicit unknowns, not arbitrary guesses.

Architecture rules also need the right edge universe. A type-only dependency may violate an inward-dependency rule even though it cannot execute. Conversely, a known constructor injection edge must not become a fabricated method call. Include external package references in boundary checks; ignoring dependencies outside the indexed entity graph would hide a domain import of an ORM or cloud SDK.

Research into pattern detection models both structural features and semantic roles; it does not justify promising perfect automatic recognition of every idiom. Patterns can be overlapping, distributed across files, implemented with functions, or indistinguishable by a small graph motif. Declared intent makes deterministic checks much stronger

A user could declare that domain/** owns policy, application/** owns use cases and port contracts, infrastructure/** supplies adapters, and a composition root may wire everything. Codiluce can then check dependency rules, exceptions, and coverage without an LLM. These paths are an illustrative policy, not a new configuration format or a requirement that repositories use those folders.

Give conflicts and ambiguity first-class outcomes: overlapping role assignments, conflicting allow/deny rules, unassigned symbols, unsupported facts, and environment-conditional bindings. Prefer violated, no violation found in checked scope, and inconclusive over an unconditional architecture “pass.” A high-confidence source fact does not make the broader interpretation high-confidence.

Where an LLM helps

  • Suggest initial role mappings, bounded-context candidates, and names using source, glossary, ADRs, tests, and existing graph neighborhoods.
  • Explain a deterministic result and why it might matter; distinguish competing interpretations such as State versus Strategy or Decorator versus Proxy.
  • Propose review questions and refactor options, with source-linked evidence and explicit assumptions.

Keep LLM output in the annotation/explanation layer. Require structured participant references and evidence links, validate those references, and reject invented participants or unsupported relationship claims. Cache by evidence and prompt/model versions; mark suggestions stale when dependencies change. Schema validation and link existence still do not verify semantic claims. Temperature zero is not a reproducibility or correctness guarantee. Human-confirmed mappings can become versioned declarations checked deterministically afterward.

What is too complex for the first release

General LSP certification, complete semantic DRY detection, inferred business invariants, universal thread-safe Singleton proofs, complete idempotency guarantees, and distributed recovery correctness should not be initial automated claims. Arbitrary reflection, metaprogramming, dynamic configuration, unindexed dependencies, and cross-process behavior require more than a static repository graph. LLMs do not remove these evidence limits. Bounded checks and useful partial visuals remain achievable.

Compatibility is specific to the feature

A language may supply file recognition, structural declarations, resolved imports, direct calls, framework routes, or effect facts at different levels. None alone establishes complete contract, DI, construction, delegation, or type-use analysis. The explicit per-file support model in src/analysis/facts.ts and src/analysis/capabilities.ts already recognizes this distinction. For architecture features, support must be tracked per detector and prerequisite as well as per language/framework.

Many object-oriented patterns are not applicable to a template file; classify that separately from unsupported extraction.

Build the semantics once per family, then share detectors

The cost should not be modeled as “24 languages × 24 frameworks × every pattern.” Most language/framework pairs are not valid combinations, several entries share infrastructure, and many patterns are framework-independent. The reusable design is: language facts + framework registrations → normalized semantic facts → shared pattern detectors and architecture checks.

In the current pipeline, richer resolution is concentrated in roughly eight implementation families: TypeScript/JavaScript, PHP, Python, Ruby, Go, Rust, JVM, and C#. Embedded component formats can reuse parts of the TypeScript path. This grouping reduces duplicated work, but does not erase differences between Java and Kotlin, typed TypeScript and JavaScript, or individual framework versions.

The common model should represent a callable or object satisfying a contract, consumers, implementations, construction, delegation, state/effects, registrations, conditions, and source proof. A Strategy detector can then operate on a normalized “consumer delegates through contract to alternatives” shape. Language adapters decide whether the evidence establishes that shape through interfaces, functions, protocols, traits, or another supported mechanism. Do not infer an implementation merely because names or signatures look alike.

Framework recipes remain necessary. Nest has token, value, factory, and alias providers; Spring has environment-selected bean definitions; .NET has service registrations and lifetimes. Those mechanisms need separate extraction rules even if all produce a common binding fact. Go interfaces are satisfied implicitly rather than through an explicit implements declaration. Primary documentation: Nest providers, Spring environment, .NET DI, Go interfaces.

Separate the complexity of extraction from the claim being made

  • Declared role overlays: low–medium. Assign roles by explicit selectors and display them in any recognized language. This visual coverage can be broad before semantic checking is broad.
  • Generic dependency rules and cycles: medium for the shared engine. Per-ecosystem extraction can still be high or very high where import/type/reference resolution is missing. Rules can report witnessed violations with partial coverage, but cannot certify absent violations outside that coverage.
  • Automatic architecture-role suggestions: medium for conventions, high for meaningful inferred boundaries. Folder/framework conventions are useful candidates. Determining business policy or bounded contexts needs intent and domain context.
  • Selected pattern recognition and explicit DI wiring: high. They need language-specific semantic enrichment, framework-specific registrations where applicable, hard-negative fixtures, and real-repository validation.
  • All GoF variants and advanced behavioral guarantees across all entries: very high, with fundamental scope limits. Equivalent static completeness is not a credible universal commitment. Contracts, supported build contexts, runtime inputs, and explicit “unknown” outcomes remain necessary.

Rules are not all recoverable from source

The observed dependency graph describes what the code depends on. It does not establish that the team intended “domain must never depend on infrastructure,” which exceptions are legitimate, or which business invariants matter. Import existing architecture-test declarations or explicit project rules when available; otherwise let users confirm a suggested policy. A deterministic checker verifies the declared policy against the observed facts. Inferring a rule from current code and checking the same code against it risks approving the very violation the user wanted to find.

The largest continuing costs

Validation and maintenance: aliases, shadowed APIs, conditional registrations, generated code, build settings, framework upgrades, omitted external dependencies, callbacks, and dynamic code all need regression cases. Maintain a capability matrix by fact, detector, language, and relevant framework profile; test valid combinations and adversarial examples rather than an artificial full Cartesian product. Record precision/recall for pattern instances and participant roles, plus the scope that remained inconclusive.

Pipeline and memory integration: richer facts must be emitted while the relevant semantic services are available. The current pipeline retires native-language contexts and releases TypeScript services; a new final pass should consume compact serialized facts rather than retain every compiler tree. Worker encoding, cache invalidation, versions, source provenance, memory budgets, and incremental matching therefore belong in the estimate. These are integration costs beyond writing a few AST queries.

LLM assistance reduces interpretation effort, not proof obligations. An LLM can suggest roles and patterns across many languages quickly, but needs source grounding, evaluation, stale-result handling, and confidence labels. It should not fill a missing deterministic dependency with a fabricated edge or turn an inferred policy into an enforced rule without confirmation.

Planning recommendation: treat the first constrained slice as a feature and broad reliable coverage as a multi-release analyzer initiative. Start with declared architecture rules and a handful of patterns in TypeScript/Nest, then test portability in a structurally different ecosystem such as PHP/Laravel. Expand by prerequisite capability and supported profile. Include the structural-only languages in the role overlay early, while clearly distinguishing their limited semantic checks.

No calendar estimate is claimed here. A credible estimate needs fixed detector scope, language/framework versions, accuracy targets, supported build inputs, staffing, and measurements from at least two representative end-to-end slices. Full automatic semantic parity across every entry is an unsuitable release criterion.

A staged delivery approach

The principal engineering cost is collecting the right semantic facts per language and framework, then validating the detectors. Rendering a role badge or a small diagram is comparatively straightforward. The following sizes are relative engineering judgments, not elapsed-time estimates.

  1. Make existing dependencies explorable Small–medium

    Add an architecture dependency projection, cycle groups, basic coupling measures, evidence navigation, and an explicit distinction between import/type/reference/call/registration edges. Reuse the map, diagram component, and existing partial Nest injection facts. Avoid claiming full DI resolution.

  2. Add declared roles and conformance rules Medium

    Support role selectors, contract ownership, module public APIs, allow/deny policies, exclusions, and exceptions with reasons. Add a configured ports-and-adapters or layered view. Check both internal relations and external package dependencies. Gate “no violation found” on declared scope and required fact coverage.

  3. Enrich the semantic facts for selected languages Medium–large

    Represent interfaces/protocols/function contracts, fields, construction sites, parameter injection, returned products, override relations, forwarding, and type-only usage. Add supported provider/token recipes with conditions. Start with a narrow well-supported language/framework pair; expand only after fixtures establish its boundaries. No changes belong in the separate multilingual worktree as part of this research.

  4. Ship a small pattern pack Medium–large

    Start with Strategy-shaped delegation, factory creation, Adapter/Decorator wrappers, standard Iterator protocols, and known Observer APIs. Use candidate labels where roles are ambiguous. Add manual confirmation and exclusion. Each detector declares required facts, supported languages/versions, and known near-misses.

  5. Add optional semantic assistance Medium

    Use the existing annotations and explanations to suggest role assignments and explain findings. LLM use stays opt-in and bounded to relevant code. It should improve naming and interpretation without being necessary for the core architecture view.

  6. Expand to behavioral and distributed patterns Large

    Add messaging contracts, infrastructure parsing, state/control/data-flow facts, and optional runtime traces or test evidence. CQRS, Saga, Outbox, aggregate invariants, and resilience guarantees should have detector-specific evidence limits. Real sequence/state layouts are separate visualization work.

A proposed analysis result

A derived design finding should record a stable ID, pattern/rule and version, participants with roles, supporting relation IDs and source locations, declaration/structural/LLM/runtime provenance, result status, unknown prerequisites, configuration digest, and snapshot/content hashes. Rules and pattern instances should live beside canonical code facts, allowing overlapping memberships and recomputation without inventing execution edges.

Use separate values for recognition basis, conformance outcome, and coverage. For example: “Architecture declared by user; one forbidden import observed; three files lack type-use coverage.” This is more useful than one opaque confidence number. Existing graph evidence confidence is not a calibrated probability of pattern correctness.

Acceptance criteria before product claims

  • Maintain positive examples and hard negatives for each detector: names that lie, unused registrations, dynamic tokens, conditional overrides, erased interfaces, closure strategies, and lookalike wrappers.
  • Measure instance-level and participant-role precision/recall per supported language and framework on labeled fixtures and representative repositories. Do not borrow a universal accuracy percentage from unrelated research.
  • Check deterministic normalized results and layouts across repeat runs with pinned inputs. Test that changing the detector/ruleset is distinguished from a code change.
  • Verify that unsupported or budget-limited analysis becomes inconclusive, that witnessed violations retain source proof, and that external package dependencies are included where policy requires them.
  • Measure extraction/rule latency, memory, incremental invalidation, and UI clutter on large repositories. Use indexed bounded motifs and anchor types; avoid unrestricted subgraph search and enumerating every cycle.

Recommended first scope: declared architecture roles + dependency rules + cycle visualization + existing DI evidence + a focused ports-and-adapters diagram. This gives a useful, explainable result without requiring an LLM. Expand automatic recognition as language facts and benchmarks justify it.
