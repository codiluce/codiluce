Codiluce · Product & integration design

One map.
Many agent harnesses.

Make ten important coding harnesses integration targets, with a shared adapter system for MCP, observed activity, session history, subagents and the characters on the map.

Roadmap and implementation · 17 October 2026 · Original ten targets, extended with OpenClaw and Hermes.

Implementation: all twelve harness families are registered, with MCP setup, native observation adapters, session filters and distinct map characters. OpenClaw and Hermes are included. New profiles remain experimental until qualified against the user's installed runtime.

Native history readers cover Codex, Claude Code, Pi, Copilot CLI, Gemini CLI and repository-scoped OpenClaw sessions. All twelve accept explicit session exports; OpenCode's native JSON export is accepted directly. See the connection guide for setup, profiles and exact coverage.

OpenCode 1.18.27 and Pi 1.3.0 passed real MCP discovery checks. Pi's resource loader loaded the generated extension without errors. The original planning baseline and proposed delivery sequence remain below for context.

Recommendation: establish the adapter contract using Codex and Claude Code, then implement OpenCode and Pi first. Expand to Cursor, Copilot and Gemini CLI next. Add Cline, Antigravity and Cascade through explicit runtime profiles.

Ship useful capabilities independently. A harness can connect through MCP before Codiluce can observe its activity or import its history. Every observed actor can use a character immediately, with a shared fallback.

01 · Starting point

We already have several kinds of compatibility.

The current checkout connects Claude Code, Codex and Cursor during MCP setup. Live hooks, connection diagnostics and imported conversations support Codex and Claude Code. The map has dedicated Clawd and Codex characters, plus Bolt as a generic fallback. These are different baselines, and the roadmap should preserve that distinction.

Reuse the existing core

The stdio MCP server and explanation tools are already independent of the calling model. Activity is normalized into a bounded observation model, streamed to the UI, and resolved against the repository. Conversation storage and the crew renderer can remain shared.

Code: MCP server, activity model, conversation store, crew behavior.

Remove the two-harness assumptions

AgentId in setup and AgentProvider in activity differ. CLI validation, API schemas, transcript discovery, connection setup, filters and display labels contain fixed provider lists. History path extraction also feeds tools into the Codex hook normalizer. Adding another union member alone would leave several of these incomplete.

Code: setup, CLI, activity routes, history paths, connections UI, character selection.

This section records the baseline before implementation. Current behavior is described in Agents: observed activity on the map and the connection guide. Documentation findings and fixture coverage do not certify every released runtime.

02 · Target portfolio

Ten targets, with honest capability boundaries.

This is a product shortlist, not a measured market-share ranking. Selection balances established editor and vendor distribution, active open-source ecosystems, usable integration surfaces, maintenance cost, and the explicitly requested OpenCode and Pi. The order below groups delivery waves rather than claiming exact popularity.

MCP lets the agent use Codiluce. Activity lets Codiluce observe the agent. History imports readable conversations. Agent identity distinguishes sessions and explicit child actors. MCP alone does not provide the other three.

03 · Harness-specific work

Use the extension surface each harness actually offers.

Baseline

01 · Codex

Move the existing MCP installer, hook generator, connection/trust checks and transcript parser behind one adapter. Preserve .codex/hooks.json and the current user MCP scope. Keep metadata-only app-server reads bounded.

Subagent hooks can share the parent session ID. A child starting does not prove subsequent parent tool observations came from that child. Keep existing codex:session-id links stable.

Baseline

02 · Claude Code

Wrap existing MCP, .claude/settings.local.json hooks and JSONL import. Preserve failure events, session titles, child IDs and sidechain history. Custom agent definitions and live child instances are separate concepts.

Use this with Codex as the regression baseline. Hook event names that look similar across products must still pass through their own payload decoder and neutral response serializer.

03 · OpenCode

Best first new adapter: native MCP, project plugins and differentiated primary/subagent roles. Generate MCP configuration and a small Codiluce plugin. Consume tool.execute.before/after, session status/idle/error and explicit permission events.

Preserve worktree and call IDs. Treat session idle as turn completion. Prefer a documented, scoped server API or export for history over reading private storage. Attaching requires an explicitly selected local server; never start a conversation to observe one.

04 · Pi

Current Pi documents native MCP and .pi/mcp.json; do not assume Pi always needs a third-party MCP bridge. Build a Codiluce extension for tool/session observations. Keep older MCP extensions and Pi forks as separately detected profiles.

04 · Scale through adapters

A shared core, with versioned harness profiles.

Harness + runtime profile→MCP config · hook · plugin · import→Validated adapter boundary→Shared activity & conversation stores→Sessions · map · crew

1. One registry owns identity and capabilities

Introduce src/harnesses/ with a registry, adapter contracts, shared config helpers and one directory per harness. Make setup, CLI validation, server routes, MCP tool schemas, session filters and UI labels consume registry metadata. Generate a small serializable manifest for the browser; browser imports must not pull in installers or transcript readers.

Use harnessId for the runtime that executes tools. Keep the host surface, model vendor/model ID, custom role definition, observed session, child agent instance and visual character separate. Claude running inside OpenCode remains OpenCode. A Codex session hosted in VS Code remains Codex.

// Illustrative contract: proposal, not an implemented API.
interface HarnessAdapter {
  id: HarnessId;                    // registry-validated, stable identifier
  label: string;
  discoveryAliases: string[];       // binary names / renamed products
  profiles: RuntimeProfile[];       // IDE, CLI, legacy versions, etc.
  presentation: { characterId: string; fallback: 'bolt' };
  detect(context: LocalContext): Promise<DetectedProfile[]>;
  planSetup(profile: ProfileId, scope: SetupScope): Promise<SetupPlan>;
  diagnose(context: LocalContext): Promise<ConnectionDiagnostics>;
  activity?: ActivityAdapter;       // decoding + neutral hook response
  history?: HistoryAdapter;         // discovery + bounded import
}

interface RuntimeProfile {
  id: ProfileId;
  versionRange: string;             // set only after fixture + smoke validation
  capabilities: {
    mcp: Capability;
    activity: Capability;
    history: Capability;
    childLifecycle: Capability;
    childToolAttribution: Capability;
    roleDefinitions: Capability;
  };
}
// Capability = support level + evidence/tested versions + known limitations.
// Levels: verified | experimental | unsupported | unknown.
// Connection state (configured/trusted/delivering) is separate.

Retain legacy provider fields and old conversation/actor keys during migration, including the setup alias claude → claude-code. Do not rewrite existing IDs or fragment links. New internal keys should encode a tuple of repository/worktree, harness, source instance, session and optional child ID instead of depending on ambiguous colon splitting. Keep any public legacy key as an alias.

2. Keep MCP as the portable foundation

  • Reuse mcpLaunch(), install-kind handling and the current stdio server. Render each client's schema: an mcpServers blob is not universal; OpenCode and VS Code already need different shapes.
  • Support explicit project/user scope, repository/worktree binding and custom state directories. Explain the chosen scope in setup. Prefer project scope for new integrations where the harness supports it; retain existing defaults during migration.
  • Expose a reviewed setup plan with exact files/commands, then use the harness CLI or a format-aware merge. Preserve unrelated MCP servers, hooks, comments and settings; malformed files must produce a useful error rather than being replaced. Track owned entries for idempotent updates and removal.
  • Maintain one explanation workflow, with small harness-specific instruction/skill wrappers where useful. MCP calls and client names must not fabricate a live session ID or imply observation of built-in tools.
  • Keep local stdio as the first goal. SSH, containers and remote hosts require a collector in the execution environment with explicit path mapping. Cloud sessions cannot deliver to a developer machine's loopback address. A remote authenticated transport is a separate milestone.

3. Normalize observations before they reach the core

Use native command hooks for script-capable products, a small OpenCode plugin, and a Pi extension. All should produce the same versioned observation envelope. Keep decoding tools and lifecycle separate from shared path validation, limits, event storage and map resolution.

// Proposed normalized envelope. Optional fields require source evidence.
{
  schemaVersion: 1,
  harnessId, profileId, sourceInstanceId,
  repositoryRoot, worktreeRoot,
  sessionId, agentId?, parentAgentId?, turnId?,
  sourceEventId?, toolCallId?, parentToolCallId?,
  occurredAt?, receivedAt,
  kind, phase, paths, status?,
  provenance: { transport, attribution: 'session' | 'explicit-child' }
}
  • Map meaning, not spelling. Keep raw event names inside adapters. The crew should consume semantic session/turn/child/tool events rather than checking strings such as SubagentStart or Stop. Each tool mapper handles its native names, arguments, error shape, paths and compound tool wrappers.
  • Preserve attempted versus completed actions. A tool starting marks an attempt. Only a successful completion confirms an edit/read. Missing completion, partial delivery or a failed tool must remain visible as uncertain or failed.
  • Keep runtime state bounded. Turn completion becomes idle; session termination becomes finished. Silence eventually becomes unknown. Session IDs are mandatory for actors; an adapter may create a stable process-scoped ID only if it owns that source and can prove its boundaries.
  • Support concurrent and repeated events. Correlate using explicit call IDs, retain arrival time as well as source time, and deduplicate stable source IDs. If no source ID exists, do not collapse identical legitimate actions just because the paths match. Avoid duplicate hooks and plugin delivery through source registration.
  • Keep observers passive. Use the profile's valid neutral hook response. Never emit a permission decision, context injection, tool mutation or continuation request for observation. Extension handlers must not modify arguments/results or throw into the agent loop. Preserve other installed hooks.
  • Retain current local boundaries. Shared validators reject foreign roots and path/symlink escapes. Keep loopback delivery, the activity request header, read-only restrictions, bounded in-memory retention and minimal metadata. Prompts, reasoning, patch bodies, raw commands and tool output stay out of activity. Existing search-query retention remains explicit.
  • Keep delivery cheap. Preserve the current 1.5-second forwarding timeout; plugins should use bounded queues and discard excess observations without slowing tools. Disconnected delivery does not become durable transcript capture or replay.

4. Make history an optional, independent adapter

Split src/conversations/import.ts into provider-specific readers feeding one public-message model. Discovery, repository ownership, selected branch, pagination, incremental checkpoints and error reporting belong in the history interface. Prefer documented APIs or exports, then provider-owned local files. Private databases are a last resort and an experimental profile.

Preserve the existing explicit import/refresh action and bounded refresh for observed sessions. An installation can show live activity while history is unavailable. Never follow an arbitrary transcript path from an event without checking its source store and project ownership. Exclude system prompts and private reasoning; retain current transcript redaction, truncation and read-only behavior.

Track source version and import stamp, handle partial writes/rotation/compaction, and leave an unsupported schema untouched with a clear explanation. Pi requires branch-aware import; a fork or a resumed session must not merge with unrelated history.

5. Treat role definitions and child instances separately

A “reviewer” definition configures behavior; a spawned reviewer is an observed actor. Record definition metadata only when explicitly available. Parent/child relationships need native IDs or a mapping from a collector that owns the session. Shared model names, agent names, paths or timing are insufficient evidence.

Observe delegation without making Codiluce an orchestrator. Optional Codiluce explainer/reviewer skill packages can be generated from shared instructions later. Do not promise portable model selection, tool permissions, nested delegation or MCP inheritance: those remain harness policies.

6. Expose capability and connection state in the product

Replace the two-button connection chooser with a searchable registry-driven list. For each installed profile show independent MCP, activity, history and child-attribution status, plus “not configured,” “needs trust,” “delivering,” “unsupported,” or “unknown” as appropriate. Receiving an event proves delivery, not saved trust or history access. Idle sessions need not emit heartbeats.

Keep provider-specific setup instructions and diagnostics in the connection dialog. In the main Agents list, offer harness, session, role and file filters only where data exists. Unknown future harness IDs should remain readable with a text label and fallback character even when ingestion requires a registered adapter.

05 · Agents at work

Every observed actor can have a character.

Separate characterId from harnessId. Keep shared poses, props, timing, movement and hit targets; register only each character's pixel rows, palette, dimensions, face crop and hand anchors. Preserve Clawd and the blue terminal cloud. Bolt remains the fallback for every integration, including future adapters.

Character direction

Existing: Claude Code → Clawd; Codex → blue terminal cloud.

Proposed original motifs: OpenCode → terminal cube; Pi → round builder with a π badge; Cursor → pointer scout; Copilot → visor pilot; Gemini CLI → twin-star explorer; Cline → notebook courier; Antigravity → floating orbit mechanic; Cascade → wave courier.

These are art directions, not shipped assets. All eight new harnesses can launch with Bolt plus their actual name while dedicated sprites are made.

Rules shared by every character

  • The harness determines the default body; the session's stable color/ring distinguishes simultaneous sessions. An optional user preference can select another skin.
  • Explicit children inherit the family with a smaller body and a visible parent relationship. Parallel tool calls are not extra child agents.
  • Movement to files requires observed paths. Commands or waiting with no path stay off-map. Missing identity never produces a fabricated actor.
  • Thinking/reply poses are illustrative when inferred; distinguish them from observed activity in the ledger. No reasoning text is collected.
  • Use the same pose set, keyboard-accessible labels, readable silhouettes, reduced-motion behavior and session link for every body.

Implementation seam: split presentation metadata from pixel-crew.ts, then remove the codex | claude-code | other routing assumption without losing the existing fallback. Keep crew.ts harness-neutral and consume semantic lifecycle events.

06 · Delivery sequence

Prove extensibility before expanding the checklist.

Each integration gets an initial discovery spike that records the exact product, release, platform, config scope, event samples, session identity, failure/neutral-response behavior and history access. Implementation estimates follow these spikes; no calendar promises are implied below.

M0 · SHARED FOUNDATION

Preserve the baselines

Add registry/contracts and migrate Codex/Claude. Keep APIs and archived links readable. Extract shared tool/path logic; make UI options and crew presentation data-driven.

Exit: existing setup, activity, history, trust and character behavior pass regression checks. A test adapter can register without editing core provider lists.

M1 · OPEN EXTENSIBILITY

OpenCode + Pi

Ship scoped MCP setup, one plugin and one extension. Add activity, session identity and Bolt fallback. Deliver Pi history after branch-aware fixtures; validate OpenCode API/export history separately.

Exit: both can publish explanations and light observed files without taking ownership of the user's conversations.

M2 · BROAD DISTRIBUTION

Cursor + Copilot + Gemini

Extend Cursor's existing MCP setup; add native hook profiles for all three. Separate Copilot CLI, VS Code Copilot and VS Code Local contracts. Add history only when a supported source passes validation.

Exit: each verified profile passes the same lifecycle, path, concurrency and disconnect scenarios.

M3 · ADDITIONAL PRODUCTS

Cline + Antigravity + Cascade

Ship MCP setup first, then verified activity profiles. Handle Cline hook generations and Cascade/Windsurf naming. Keep unsupported history or child attribution explicitly unavailable.

Exit: ten target families are represented; supported releases and capability gaps are visible and documented.

PARALLEL PRODUCT TRACK

Dedicated characters

Design and add the eight new bodies through the presentation registry. Reuse every pose and prop. Add faces to connection/session lists and a mixed-harness crew preview.

Exit: all ten have readable, accessible identities; artwork never blocks functional integration.

ONGOING

Compatibility maintenance

Record tested release ranges and fixtures per profile, monitor upstream format changes, and qualify upgrades. Add Kiro next using the same contract. Consider ACP or remote transport only for a concrete use case.

Exit: the next harness adds adapter code, metadata and fixtures without another core integration rewrite.

Suggested reviewable work packages

  1. Registry and schema compatibility: stable IDs, capability manifest, legacy aliases and old link/store compatibility.
  2. Activity boundary: separate raw decoders, shared path/tool helpers, semantic lifecycle and passive response handling.
  3. Setup and UI: installation plans, scoped config merges, profile diagnostics and registry-driven selectors.
  4. History boundary: discovery/import interface, incremental checkpoints and existing parser migration.
  5. OpenCode: MCP + plugin + event fixtures; history as a follow-up if the spike succeeds.
  6. Pi: MCP + extension + branch-aware history, with explicit supported package/profile.
  7. Remaining integrations: one family per package, split further when IDE/CLI payloads differ.
  8. Character registry and art: shared fallback first; dedicated bodies in small visual changes.

These are proposed work packages, not GitHub Issues already created. Exact test ownership and merge order should keep each intermediate build usable.

07 · Definition of done

Certify capabilities per profile.

MCP and setup

  • A clean repo and an already configured repo both get the correct scope. Applying setup twice does not duplicate entries or lose another server/hook.
  • Test checkout, installed package and npx launch paths; paths with spaces; custom state directories; two repositories and two worktrees.
  • Prove tool discovery, a real graph read, link validation and publishing an explanation. Installing hooks alone is not an MCP test.
  • Test config parsing and neutral hook output on each declared OS/runtime. Initial release qualification can start with Linux/macOS; Windows remains explicit until validated.

Activity and subagents

  • Exercise read, edit, rename/delete, search scope, command, failed tool, denied/cancelled tool, permission wait, idle turn and resumed session.
  • Run parallel tools and two sessions. Check duplicate and out-of-order events, missing completions and a child lifecycle with and without child tool IDs.
  • Prove foreign-root/symlink rejection and read-only behavior. Stop Codiluce and confirm the harness continues with normal permission handling and no added context.
  • Check the UI distinguishes delivering, trusted, configured and unavailable. Partial coverage must never become a full-support badge.

History

  • Import a real sanitized transcript/export fixture, refresh incrementally, and prove project/session identity without importing unrelated projects.
  • Cover forks, compaction, partial writes and schema changes. Pi needs a branch selection fixture; Cline needs its exact product/version fixture.
  • Check public text/tool summaries, reasoning exclusion, existing truncation rules, file associations and stable canonical links.
  • Activity-only profiles show an honest history-unavailable state. No importer is required to qualify MCP or activity support.

Characters and scale

  • Render all shared poses, left/right movement, props, list faces, reduced motion and a mixed session/subagent scene.
  • Check name labels and keyboard session navigation. Color alone cannot identify a harness or a failed action.
  • Measure that plugin delivery does not block the tool loop and that existing event/session limits still hold.
  • Add an eleventh test harness and an unknown presentation ID. Both should exercise the generic UI/fallback without a special-case renderer branch.

Build on existing activity, conversation, setup and browser coverage. Fixtures certify parsers; smoke tests certify actual integration. Record both.

Portfolio success: ten named target families; MCP setup verified for each chosen local profile; passive activity and characters wherever a supported observation API exists; history and child tool attribution only where independently proven. OpenCode and Pi must reach useful live compatibility early. The eleventh integration should need no new core provider list.

08 · Extend without another redesign

Keep the next targets inexpensive.

Kiro is the first follow-on candidate. It has documented MCP, custom agents and hook profiles, with important differences between CLI 2.x/3.x and IDE generations. It sits outside this ten-target scope to keep the initial portfolio bounded, not because it lacks an integration path. CLI · Hooks by surface · Agent configuration.

Other candidates: Continue, JetBrains Junie, Amp, Aider and editor hosts such as Zed. Promote them after checking current demand and public extension surfaces. No live activity or MCP support is assumed here. A generic MCP connection can still be documented independently of an activity adapter.

Roo Code is not a new first-class target. Its official sunset notice scheduled the extension, cloud and router shutdown for 15 May 2026. Consider legacy transcript import or an actively maintained fork only when users need it; keep fork profiles distinct. Official sunset notice.

Checklist for adding harness eleven

Choose a stable ID and exact runtime profile; document evidence and release range; register display metadata and Bolt fallback; implement detection and scoped MCP setup; add an optional activity decoder/collector and neutral response; add optional history discovery/import; supply sanitized fixtures and one real smoke test; publish the capability manifest and limitations.

Reuse the existing stdio tools, shared path checks, stores, session UI and crew. A third-party adapter loads only after explicit installation/registration; receiving an unknown ID must not auto-download code.

MCP, ACP and hosted runtimes

MCP exposes Codiluce tools to an agent. An agent/client protocol such as ACP can offer another observation source when a host owns a connection, but it is not a universal observer for arbitrary sessions. Evaluate it after the native integrations prove a concrete reuse case.

Do not bundle hosting conversations, autonomous orchestration, remote cloud ingestion or universal role/permission conversion into this roadmap's first release. They require separate contracts; the optional adapter transports leave room for them.

Evidence policy: local baseline checked against the files linked above; harness claims linked to official documentation or the project's own repository. Current documentation is a discovery source, not proof that every released client implements it. Capture immutable release/commit references with adapter fixtures during implementation.
