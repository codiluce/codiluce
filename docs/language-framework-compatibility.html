Build a common platform, then ship complete slices

Keep the TypeScript compiler and PHP parser. Add a Tree-sitter structure layer, language-specific import and reference resolvers, and versioned framework packs that emit the existing graph.

The largest investment is reliable binding and framework semantics. Parsing a function does not establish what its calls reach. Each release should show useful structure immediately and state precisely which relationships it can prove.

Architecture to build

Discover projects→Parse & declare→Resolve bindings→Apply packs→Link APIs & project

1. Separate project, language and framework responsibilities

A project model describes application identity, packages, source roots, workspace membership and dependency edges. A language adapter extracts declarations/imports and supplies language-specific scope rules. A framework pack interprets resolved API usage and conventions. The graph writer, evidence machinery and diagnostics are shared.

src/analysis/
  registry.ts           # adapters, packs, capability declarations
  project-model.ts      # workspaces, source roots, dependencies
  source-map.ts         # original-file coordinates, embedded regions
  facts.ts              # declarations, imports, bindings, registrations
  symbols.ts            # scoped declaration index and identity
  tree-sitter/          # runtime, grammar loader, query loader
  languages/            # python, go, ruby, rust, java, csharp, kotlin...
  resolution/           # shared outcomes/traces; language-owned rules
  routing/              # patterns, composition, method/host constraints
  frameworks/           # express, nestjs, django, vue, rails...

2. Define a small shared fact model

  • LanguageAdapter: ID/version, applicable file types, grammar/parser, capability flags, declaration/import extraction, scope and binding rules, optional embedded regions.
  • FrameworkPack: ID/version, ecosystem and tested framework versions, activation evidence, required capabilities, detection/registration/linking stages, emitted features and diagnostic codes.
  • Declaration: owning project/file, lexical scope, qualified name, kind, signature, source range, visibility/export status and content/body hashes. Keep parser trees behind adapter interfaces.
  • ImportResult: resolved target(s), external dependency, ambiguous candidates, unresolved reason, unsupported form or excluded target. Include specifier, bindings/aliases, dependency kind and an evidence trace.
  • EndpointFact: route pattern, methods, handler(s), application, registration state, mount chain, conditions, middleware roles/order, source anchors and framework version.

Declare all files and symbols before cross-file linking. Evaluate re-exports, mounts and constant aliases with a bounded work queue and cycle detection. Reuse SiteCollector for resolved sites, counts and effects; add forms as needed without presenting dependency injection as an ordinary source-level function call.

3. Add Tree-sitter as structural infrastructure

Start with web-tree-sitter and packaged WASM grammars as the distribution candidate; benchmark it against the existing workload before committing. Its documented loading model supports explicit language WASM assets. Pin the runtime, grammar revision, ABI and asset checksum together. Tree-sitter WebAssembly binding.

  • Build grammars in Codiluce release tooling; ship validated assets and licenses in the npm package. End users should need only the existing Node runtime. Load a grammar only when its language is present.
  • Own the extraction queries. Use maintained grammars as candidates, but qualify each against the exact syntax supported. The upstream parser inventory is a discovery list, not a guarantee of equal quality. Grammar inventory.
  • Normalize zero-based parser positions into Codiluce’s source-range convention. Test Unicode, emoji, CRLF, tabs and exclusive end positions. Verify the selected binding’s index units instead of assuming every parser uses byte offsets.
  • For parse errors, keep valid declarations outside damaged regions and record partial status. Suppress relationships whose required syntax intersects error/missing nodes. Use worker cancellation and bounded parse/query budgets; release trees and parsers predictably.
  • Cache extracted facts by content + grammar + query + adapter version. Persist serializable facts rather than parser objects. Cross-file results also depend on the project graph and resolver inputs.

4. Make embedded languages first-class

Represent Vue, Svelte, Astro, ERB and Razor as original files containing language regions. Track script/module/frontmatter/template/style ranges; produce one canonical component identity and map generated or virtual JS/TS back to the original file. Preserve server/client execution context.

Tree-sitter injection queries can describe embedded regions, but the host application still needs orchestration and mapping. Evaluate official Vue/Svelte/Astro parsers when their ASTs preserve component semantics better than a community grammar. A component-parser dependency parses source; it must not execute the target project’s configuration or plugins. Tree-sitter language injections, Vue SFC structure.

5. Preserve deterministic, offline analysis

All resolvers should read through one indexed repository abstraction, shared by working-tree and history analysis. Do not make resolution depend on installed target dependencies, a machine’s package cache, environment, runtime imports or build output. This also closes the current difference between the restricted TS program host and import extraction that calls ts.resolveModuleName(..., ts.sys).

Use literal configuration and explicit overrides for otherwise dynamic source roots. Record external references as metadata or dependency facts without inventing local source targets. Keep configured assumptions visible in evidence. Analyze files outside detected applications for structure; add flow analysis only when their project context is defined.

Generalize routes and client/server matching

Keep the original route expression and dialect, plus a normalized pattern tree: literals, parameters, optional groups, catch-alls and opaque constraints. A string replacement that turns every route into /:id loses information needed to prevent false matches.

  • Composition: join app base paths, nested router prefixes and local patterns. Preserve mount-instance identity, registration order and all evidence hops. A router mounted twice produces two endpoint registrations with one shared handler.
  • Methods: represent explicit sets, wildcard methods, unknown methods and framework-derived HEAD/OPTIONS separately. Do not assume Django paths imply GET or expand every framework’s “all” into the same finite list.
  • Constraints: preserve host/subdomain, version, slash/case sensitivity, converters, regex, headers, query and content-type restrictions. Only evaluate supported constraints; otherwise retain candidates and report uncertainty.
  • Registration: distinguish declared router, proven mount, documented convention, conditional mount and unknown reachability. Do not show every controller-looking class or unused router as a deployed endpoint.
  • Boundaries: make same-application origin and explicit API origin/proxy mappings framework-neutral. Prove the server origin for browser requests; an SSR/backend relative URL is not automatically a browser same-origin request.
  • Ambiguity: a unique-looking path is insufficient when the origin, method or competing constraints are unknown. Keep the current conservative behavior and expose candidate explanations.
  • Flows: a confirmed client → endpoint → handler chain should work across every new pack using existing graph relations. Further steps depend on that language’s reference/effect capabilities. Keep response classification and branch-guard coverage visible independently.

Acceptance example: a Vue component calls a shared TS API wrapper whose configured origin belongs to a FastAPI application. The graph links the request to the prefixed APIRouter endpoint and its handler, with original-file evidence on each hop. An equally matching second server or unknown router prefix prevents the confirmed link.

Identity, history and schema rules

Base new declaration IDs on project/module identity, lexical scope, kind and normalized signature, with deterministic disambiguation for same-name declarations. Avoid line numbers as primary identity. Preserve declaration fragments for Ruby reopenings and C# partial types. Route identities must distinguish mount instances, methods and constraints without depending on discovery order.

Retain current TS/PHP identity recipes during extraction; a universal ID redesign should be a separate migration. Add analysis provenance/capability metadata to the appropriate derived/positional exclusions in history/fingerprint.ts so parser upgrades do not masquerade as source edits. Update snapshot readers, version comparison and cache format together when contracts change.

Release criteria and test strategy

Keep compact conformance fixtures for each supported construct and negative case. Add a small, pinned set of reviewed open-source samples per ecosystem for realistic validation. Dependency installation must never be required during ordinary analysis.

  1. Structure: exact names, scopes, kinds, ranges and fingerprints; nested/anonymous/overloaded declarations; valid fragments in damaged files; no duplicate entities.
  2. Imports: relative, aliased, re-exported, cyclic, ambiguous, excluded and external dependencies; same names in unrelated modules; workspace packages; malformed config and missing files.
  3. Frameworks: root/nested/multiply mounted routers, imported handlers, app factories, inline callbacks, namespaces/decorators, version syntax, dynamic prefixes, unused registrations and lookalike APIs.
  4. Flows: positive client → endpoint → handler fixtures for each pack; negative cases for unknown origins, competing endpoints, constraints, unproven mounts and missing binding information. Template callbacks must keep original coordinates.
  5. Determinism: canonical graph equality with/without cache, changed file iteration order and installed target dependencies. Compare working tree and materialized commit under equivalent inputs, excluding expected run/Git-only fields.
  6. Invalidation: edit a manifest, lockfile, alias config, workspace source, route prefix, query file, grammar version or build flag; affected results must recompute. Check consumers of changed shared packages.
  7. History: insert blank lines without identity churn; rename declarations with lineage evidence; alter a mounted prefix with a meaningful route diff; record analysis-version mismatch rather than claiming all resulting differences are code edits.
  8. Packaging and resilience: npm tarball loads every advertised grammar from an unrelated directory; missing/corrupt grammar yields a bounded diagnostic; huge/broken files respect limits; repeated history indexing does not leak trees or exceed memory budgets.

Measurable promotion gates

Conformance: 100% of explicitly supported fixture constructs produce their reviewed expected graph; all deliberate ambiguity/lookalike fixtures produce zero invented confirmed links. Every linked entity/relation has valid evidence and every graph passes validateGraph.

Real repositories: manually review a stratified sample of declarations, local import edges, endpoints and handler links. Proposed beta target: at least 98% precision on reviewed confirmed edges and at least 90% recall for the declared supported routing subset. Publish sample sizes and failures per pack; these thresholds do not describe unknown real-world accuracy or unsupported forms.

Performance: set actual budgets in P0 from fixed small/medium/large samples. Suggested guardrail: existing TS/Laravel median indexing and peak memory should not regress by more than 10% after lazy infrastructure is added, measured across repeated runs on the same host. Track cold parse, warm replay, full history, grammar-load time and tarball size separately.

Checks per implementation phase: run focused conformance tests, npm test, npm run typecheck and npm run build; run package tests for shipped assets and representative end-to-end flows when API/UI behavior changes. Follow the existing architecture document’s representative-repository index check. Target application build/tests are unnecessary for static analysis.

This planning change does not implement these checks or claim they passed. The document itself is validated separately for links, layout and browser behavior.

Decisions and risks to settle early

  • Parser distribution: WASM is the preferred candidate for a Node-only install; validate startup, throughput, ABI compatibility and asset size before locking it in. A native alternative is justified only by measured gains and viable cross-platform packaging.
  • Semantic depth: Tree-sitter supplies syntax, not a compiler’s type system. Ship lexical/direct/static binding first. Optional compiler-derived indexes or language-server integrations can improve hard cases later but must preserve the default offline workflow and disclose their provenance.
  • Build metadata: Gradle, MSBuild, Ruby routes and Python settings can contain executable logic. Read the supported static subset and allow explicit configuration; do not silently simulate the full build/runtime.
  • Feature configurations: Rust cfg, Go tags, Java source sets, .NET target frameworks and conditional exports may describe multiple graphs. Record the chosen configuration and conditionally active facts rather than conflating mutually exclusive variants.
  • Cache architecture: the current graph-patch cache does not automatically restore a new symbol table or registration-fact store. Design fact persistence/reconstruction before packs consume cached language outputs.
  • Entity growth: broaden declaration kinds carefully. A new graph kind touches type unions, layout, inspector, coverage, history, annotations and storage assumptions. Preserve distinct struct/trait/interface semantics even if the first UI uses a shared type representation.
  • Scope control: initially prioritize route inventory and handler connectivity. ORM migrations, queues, authentication, templates, scheduled work, GraphQL, gRPC and websocket behavior each need independent packs or effect rules.
  • Version maintenance: every pack needs tested version profiles and diagnostics for unknown combinations. Avoid hardcoding current documentation behavior as a rule for all historical commits.

First implementation tasks

Start with these reviewable changes. They establish the common machinery without requiring every framework to be designed in advance.

  1. Freeze current behavior: add representative graph/identity/coverage expectations for the existing fixture repository and TS/PHP import edge cases.
  2. Introduce capability contracts: add registry types and per-file outcomes; wire API/coverage support labels with existing analyzers as adapters.
  3. Qualify the runtime: package one pinned Python grammar and query set; verify npm tarball loading, error handling, Unicode ranges and bounded parser lifetime.
  4. Ship Python structure: declarations, scopes, hashes and source links, including files outside detected applications.
  5. Unify project I/O: create indexed-only resolver access and explicit source-root/workspace metadata; adapt TS import extraction and prove history parity.
  6. Implement one resolver slice: Python relative/absolute imports, package initializers and aliases with explained outcomes and cycle handling.
  7. Normalize endpoints: define method/path/registration/mount facts; adapt existing Next.js/Laravel outputs with graph regression checks.
  8. Deliver Express: literal route + imported handler + mounted router, then nested registration and supported version patterns.
  9. Exercise the full graph: a TS client calling an Express/FastAPI endpoint through a proven origin, with ambiguous alternatives producing a gap.
  10. Re-estimate and expand: use measured implementation effort, correctness and performance to sequence the remaining adapters and packs.

Recommended first commitment: make P0–P3 the first milestone with separate releases along the way. Preserve P4–P10 as an ordered backlog, revising estimates after the first resolver and mounted-router implementation.
